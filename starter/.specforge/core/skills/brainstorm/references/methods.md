# Brainstorm Methods

本文件承载 Brainstorm 的内部方法库。它不是独立 skill 列表；只有 `brainstorm/SKILL.md` 和 `brainstorm-playbook.md` 决定本轮读取哪些方法。

## Problem Framing

用途：把模糊请求重构为目标、用户、痛点、约束、成功标准、非目标和必须确认问题；不做方案选择。

读取：

- 用户原始请求和最近对话。
- 已有 `brief.md`、`brainstorm.md`、PRD、requirements、UI design、technical design。
- 能说明约束的 wiki、manifest、lockfile 或代码事实；没有读取到时写 `unknown`。
- 事实会改变取舍时转入 `references/research-source.md`，不要凭记忆补。

步骤：

1. 用一句话重述原始请求，保留用户真正关心的对象。
2. 判断工作对象：产品、页面、流程、agent skill、架构、运营机制、验证方案或决策本身。
3. 分离“问题”和“用户已经暗示的解法”。
4. 填写问题重构表，缺失但会影响范围、成本、体验、架构或安全的项标记为 `[必须确认]`。
5. 标出固定约束、可改变空间、明确不做和可安全默认。
6. 列出事实查证问题。
7. 按优先级输出问题地图：核心目标/范围 > 体验方向 > 数据与安全 > 集成与依赖 > 交付验收。

输出：

```md
## 问题重构

| 维度 | 当前理解 | 缺口 / 风险 | 处理 |
|---|---|---|---|
| 原始表述 | | | preserve / rewrite |
| 真实目标 | | | confirmed / must-confirm / default |
| 用户 / 受众 | | | confirmed / must-confirm / default |
| 当前痛点 | | | confirmed / must-confirm / default |
| 成功标准 | | | confirmed / must-confirm / default |
| 固定约束 | | | confirmed / must-confirm / default |
| 可改变空间 | | | confirmed / must-confirm / default |
| 明确不做 | | | confirmed / must-confirm / default |
| 需要事实查证 | | | research-source / no-action |

## 问题地图

- [已明确]
- [必须确认]
- [可安全默认]
```

质量门槛：

- 至少区分目标、用户、约束、非目标和成功标准。
- 必须把 agent 假设和用户确认分开。
- 必须说明是否需要事实查证。
- 不能在问题未框定前进入方案推荐。

## Divergent Thinking

用途：扩大方案空间，让后续 critique 和 matrix 有真正不同的候选可以比较。

前置输入：

- `问题重构` 和 `问题地图`。
- 当前事实证据；如果事实会影响可行性，先查证再发散。
- 用户明确的非目标、固定约束和授权默认。

发散镜头：

| 镜头 | 提示 |
|---|---|
| 第一性原理 | 最小机制是什么？不依赖当前解法还能不能达到目标？ |
| 用户角色 | 普通用户、管理员、运营、开发、测试、安全分别最在乎什么？ |
| 时间尺度 | 1 天、1 个 sprint、1 个季度、长期演进分别怎么做？ |
| 成本反转 | 如果只有一天怎么做？如果维护成本最重要怎么做？如果预算充足怎么做？ |
| SCAMPER | 替换、组合、调整、放大、缩小、挪用、删除、重排。 |
| 反向失败 | 如果故意做差会怎么做？反过来能得到什么方向？ |
| 分层拆解 | 能力层、交互层、数据层、安全层、落地层、演进层分别有什么方案？ |

数量要求：

| Profile | 最小方向数 | 必须包含 |
|---|---:|---|
| `clarify-light` | 3 | 保守版、标准版、简化或反直觉方向 |
| `product-discovery` / `experience-exploration` | 5 | 保守版、标准版、激进版、实验版、反直觉版 |
| `technical-decision` / `research-heavy` | 2 | 至少一个低风险方向和一个依赖证据的方向 |

输出：

```md
## 发散方向池

| 方向 | 类型 | 核心想法 | 适合场景 | 主要代价 | 最大未知 | 是否进入收敛 |
|---|---|---|---|---|---|---|
| 保守版 | low-cost | | | | | yes / no |
| 标准版 | balanced | | | | | yes / no |
| 激进版 | high-upside | | | | | yes / no |
| 实验版 | exploratory | | | | | yes / no |
| 反直觉版 | counterintuitive | | | | | yes / no |
```

质量门槛：

- 方案必须在机制上不同，不能只是措辞不同。
- 每个方向都要写代价和未知。
- 至少保留一个“做少一点”的简化方向。
- 至少保留一个挑战原始假设的反直觉方向。

## Analogy Thinking

用途：当直接发散变窄、方案同质化、用户要求更高级或差异化时，从其他产品、行业、系统或内容形态提取可迁移机制。

类比来源池：

| 目标 | 可参考领域 | 可迁移机制 |
|---|---|---|
| 信任 / 可审计 | 银行后台、合规审查、病历、法律 redline | 证据链、版本差异、审批记录、责任边界 |
| 快速重复工作 | IDE、表格、CRM 队列、命令面板 | 快捷操作、批量处理、局部预览、可撤销 |
| 引导创建 | 报税、设计工具、配置向导、onboarding | 分步收集、即时校验、缺口提示、保存草稿 |
| 长期进展 | 学习路径、事故响应、项目看板 | 阶段目标、反馈回路、里程碑、复盘 |
| 探索筛选 | 市场地图、素材板、搜索 facets、科技树 | 多维筛选、组合探索、局部展开、路径比较 |
| 质量审查 | Code review、医学二诊、风控模型、出版编辑 | 反方检查、证据等级、阻断项、建议级别 |

迁移模式：

| 模式 | 适用场景 |
|---|---|
| 流程迁移 | 当前问题缺少步骤和节奏 |
| 反馈迁移 | 用户不知道系统状态 |
| 审计迁移 | 需要可信和可追溯 |
| 组合迁移 | 单个机制不够，需要组合成工作流签名 |

输出：

```md
## 类比迁移

| 来源领域 / 产品 | 相似任务 | 可迁移机制 | 当前问题中的方案 | 不能照搬 | 状态 | 风险 / 查证 |
|---|---|---|---|---|---|---|
| | | | | | ready / needs research / needs revision | |
```

质量门槛：

- 写相似任务，不只写相似产品名。
- 迁移机制，不迁移品牌、审美或专有细节。
- 必须写“不能照搬”。
- 类比涉及竞品事实时转入 `research-source`。

## Scenario Simulation

用途：把候选方向放进真实用户输入、失败路径、边界条件、权限、安全、运营维护和下游交接场景中压测。

场景优先级：

| 优先级 | 场景 | 触发条件 |
|---|---|---|
| 必须 | 失败路径 | 有候选方案进入推荐或比较 |
| 必须（有 UI） | 首次使用 / 新手进入 | 涉及页面、交互、信息架构、引导或空状态 |
| 必须（有依赖） | 技术依赖失败 | 涉及新增依赖、版本升级、AI provider、外部服务或运行时约束 |
| 按需 | 权限 / 安全 | 多角色、敏感数据、导出、审批、回滚或隐私边界 |
| 按需 | 运营维护 | 长期成本、内容维护、模型 / 依赖费用或人工流程敏感 |

输出：

```md
## 场景模拟

| 方案 | 场景 | 用户输入 / 状态 | 系统表现 | 风险 | 需要调整 | 影响推荐 |
|---|---|---|---|---|---|---|
| | | | | | | yes / no |
```

质量门槛：

- 不只写理想路径，必须包含失败或边界路径。
- 场景要具体到用户动作和系统响应。
- 暴露新的高影响决策时加入 `[必须确认]`。
- 不影响推荐时允许写 `N/A + 理由`。

## Critic Review

用途：在推荐之前检查候选方案的用户价值、隐藏假设、失败模式、过度设计、维护成本、安全隐私风险、事实缺口和范围越界。

审查问题：

| 维度 | 要问的问题 |
|---|---|
| 用户价值 | 这个方案解决核心痛点，还是边缘便利？不用它会怎样？ |
| 假设 | 哪些条件必须为真？如果不成立，方案是否崩掉？ |
| 简化 | 有没有更小版本能获得 80% 价值？ |
| 维护 | 未来谁维护？哪些依赖、配置、文档、流程会持续消耗？ |
| 安全 / 隐私 | 是否扩大数据访问、保留、导出、日志或审批面？ |
| 可行性 | 是否依赖未查证版本、API、竞品事实或用户上下文？ |
| 范围 | 是否把下游规格、设计或实现提前写死？ |
| 回退 | 方案失败时能否回滚、降级或保留旧路径？ |

输出：

```md
## 批判质疑

| 方案 | 可能不成立的点 | 最弱假设 | 更简单替代 | 需要验证 | 处理建议 |
|---|---|---|---|---|---|
| | | | | | keep / simplify / split / reject / research |
```

风险分级：

- 阻断：会改变范围、架构、安全、成本或用户承诺，写入 `[必须确认]` 或 research。
- 重要：不阻断当前方向，但影响实现复杂度或验收，写入交接和验证点。
- 轻微：只影响表达、微文案或后续细化，保留为下游注意事项。

## Decision Matrix

用途：把候选方案从想法列表变成透明取舍。它可以给 Agent recommendation，但不能把推荐写成用户已批准。

默认评估维度：

| 维度 | 方向 | 评分提示 |
|---|---|---|
| 用户价值 | 越高越好 | 对真实问题的解决力度，而不是功能数量 |
| 实现成本 | 越低越好 | 工程、设计、沟通、迁移、维护成本；用 `低 / 中 / 高` |
| 新颖度 | 越高越好 | 是否带来差异化或新洞察 |
| 风险 | 越低越好 | 安全、隐私、复杂度、采纳、合规、依赖风险；用 `低 / 中 / 高` |
| 落地性 | 越高越好 | 当前上下文和周期内是否能推进 |
| 可扩展性 | 越高越好 | 后续是否能演进，不制造大返工 |
| 证据置信度 | confirmed / likely / unclear | 事实支撑程度 |
| 下一步适配度 | 阶段适配 | 是否适合进入 PRD、requirements、UI、tech design 或 research |

输出：

```md
## 方案评估矩阵

| 方案 | 用户价值 ↑ | 实现成本 ↓ | 新颖度 ↑ | 风险 ↓ | 落地性 ↑ | 可扩展性 ↑ | 置信度 | 推荐 |
|---|---:|---|---:|---|---:|---:|---|---|
| | 1-5 | 低 / 中 / 高 | 1-5 | 低 / 中 / 高 | 1-5 | 1-5 | confirmed / likely / unclear | adopt / test / defer / reject |

## 推荐方案

- Agent recommendation：
- 为什么现在选它：
- 不选其他方案的原因：
- 需要用户确认：
- 下一步验证：
- 回退点：
```

质量门槛：

- 至少比较 2 个真实不同方案；只有 1 个方案时写明为什么没有可比项。
- 推荐必须附带放弃代价。
- 用户确认和 Agent recommendation 必须分开。
- `unclear` 不能直接 `adopt`。
- 不用单一总分掩盖高风险项。

## Output Shaping

用途：根据 profile 选择稳定输出结构，避免自由散文或 light profile 被完整模板撑爆。

Profile Section 矩阵：

| Section | skip | light | deep | research-heavy |
|---|---|---|---|---|
| 执行配置 | 必填 | 必填 | 必填 | 必填 |
| 一页摘要 | -- | 必填 | 必填 | -- |
| 问题重构 | -- | 必填 | 必填 | 必填 |
| 当前事实与研究证据 | -- | 按需 | 必填 | 必填 |
| 发散方向池 | -- | 必填 | 必填 | 按需 |
| 类比迁移 | -- | N/A 可 | 必填 | N/A 可 |
| 场景模拟 | -- | N/A 可 | 必填 | N/A 可 |
| 批判质疑 | -- | 必填 | 必填 | 必填 |
| 方案评估矩阵 | -- | 必填 | 必填 | 必填 |
| 推荐方案 | -- | 必填 | 必填 | 按需 |
| 用户确认记录 | -- | 必填 | 必填 | 必填 |
| 下一步行动 | 必填 | 必填 | 必填 | 必填 |
| 用户确认问题 | 必填 | 必填 | 必填 | 按需 |

压缩规则：

- 用户只需要下一问：输出一句背景、2-3 个选项和一个问题。
- 候选方案很多：先输出分组和 Top 3，不展开所有细节。
- 事实证据很多：只保留影响取舍的证据。
- 下游要接手：优先保留交接表、阻断条件和 owner。

## Execution Planning

用途：把“推荐或确认方向”转成下一步谁拿什么继续；不越权写 PRD、requirements、technical design 或 implementation tasks。

执行步骤：

1. 判断当前状态：已确认、Agent recommendation、授权默认、仍需用户拍板。
2. 未确认时停止行动计划，输出一个最高优先级问题。
3. 已确认时选择下游阶段：`sf-prd`、`sf-requirements`、`sf-ui-design`、`sf-tech-design`、`sf-discovery`、`sf-verify`。
4. 写 MVP 路线：Now / Next / Later，明确不做什么。
5. 写交接：下游需要读取哪些输入、产出什么、阻断条件是什么。
6. 写验证入口：事实补证、原型验证、技术 spike、用户确认、回归测试。
7. 写回退点：如果推荐失败，退回哪个方案或保守路径。

输出：

```md
## 下一步行动

| 步骤 | Owner | 输入 | 输出 | 进入条件 | 阻断条件 |
|---|---|---|---|---|---|
| | user / agent / sf-prd / sf-requirements / sf-ui-design / sf-tech-design / sf-discovery / sf-verify | | | | |

## MVP 路线图

| 阶段 | 做什么 | 不做什么 | 验证 |
|---|---|---|---|
| Now | | | |
| Next | | | |
| Later | | | |
```

路由判断：

| 条件 | 下一步 |
|---|---|
| 产品范围和用户价值仍需整理 | `sf-prd` |
| 行为、边界、验收标准需要落地 | `sf-requirements` |
| 页面、流程、状态、视觉方向需要设计 | `sf-ui-design` |
| 技术栈、依赖、架构、集成、验证策略需要设计 | `sf-tech-design` |
| 事实冲突、实验或 PoC 才能判断 | `sf-discovery` research |
| 已有可验证实现，需要证明行为 | `sf-verify` |

质量门槛：

- 没有用户确认或授权默认时，不写实现计划。
- 每个行动都要有 owner、输入、输出和进入条件。
- MVP 路线必须写“不做什么”。
- 需要 research / spike / prototype 的风险不能被隐藏在 Later。
