# 边界规则

SpecForge 采用边界优先。一个规格的价值在于说明哪些内容可以独立变化，而不会让系统其他部分意外受影响。

## 核心原则

- 一个 change 必须只有一个主要 owner。跨 owner 工作应拆分，或在 design 中写清协调方式。
- 一个 change 可以触碰多个模块，但必须说明为什么这些模块属于同一变更。
- 范围不是文件列表本身，而是责任边界、契约边界和验证边界的组合。
- 如果实现中发现边界需要扩大，必须先更新 spec 或追加 review 记录，再继续实现。
- 不用“顺手”“顺便”“为了以后”扩大范围。未来能力只在当前需求明确需要时进入本 change。

## 必答边界问题

每个非 lite change 都应回答：

- 本次变更拥有什么责任？
- 本次变更明确不负责什么？
- 依赖哪些上游契约？
- 如果契约变化，哪些下游区域需要重新验证？
- 哪些文件或模块属于允许写入范围？
- 是否涉及公共 API、数据库 schema、配置、权限、部署方式或长期文档？
- 如果本 change 被回滚，哪些行为必须恢复，哪些数据或配置需要额外处理？

## 边界产物

| 产物 | 边界职责 |
|---|---|
| `brief.md` | 候选边界和 workflow 路由 |
| `requirements.md` | 范围、非目标、依赖、验收标准 |
| `design.md` | 边界承诺和文件结构计划 |
| `tasks.md` | 任务级 `_Boundary:_` 和 `_Depends:_` 标注 |
| `code-review-v1.md` | 边界违规发现 |
| `ssot-sync.md` | 长期契约更新 |

## owner 判断

| 类型 | owner 判断方式 |
|---|---|
| 功能 owner | 谁负责该能力的行为、验收和长期维护 |
| 数据 owner | 谁定义字段含义、生命周期、权限和迁移策略 |
| API owner | 谁定义入参、出参、错误码、兼容策略和文档 |
| UI owner | 谁负责交互、状态、空态、错误态和可访问性 |
| 运行 owner | 谁负责配置、部署、监控、告警和回滚 |

当 owner 不清楚时，不能用默认假设继续推进。应在 `brief.md` 或 `requirements.md` 中标记 `[NEEDS CLARIFICATION: owner]`。

## 写入范围

`design.md` 必须写清允许写入范围：

- 允许新增、修改、删除的目录或模块。
- 只读参考的目录或模块。
- 禁止触碰的目录或模块。
- 需要用户确认的高风险文件，例如迁移脚本、权限配置、生产部署文件。

实现中如需越界，必须满足至少一个条件：

- 该文件是实现当前验收标准不可避免的依赖。
- 上游契约存在缺陷，并已记录为本 change 的设计修正。
- 用户明确批准扩大范围。

## 拆分规则

出现以下情况时，应优先拆成多个 change：

- 同时改变需求行为和大规模重构。
- 同时改变多个 owner 的公共契约。
- 同时包含前端、后端、数据迁移、部署和权限，且无法一次验证。
- 验收标准超过一个独立用户目标。
- 任何一个子任务失败都会让其他子任务无法审查。

不需要拆分的情况：

- 同一行为需要同步修改测试、文档和少量适配代码。
- 小范围重命名或局部整理是当前实现的直接前置。
- bugfix 的复现、修复、回归验证属于同一故障链路。

## 边界违规

审查时重点标记：

- 未更新规格就编辑批准范围外的文件。
- 给本变更增加属于其他 change 的责任。
- 把上游缺陷隐藏在下游补丁里。
- 创建没有明确 owner 的共享抽象。
- 契约变化后没有重新验证下游依赖。
- 为了通过测试而改变无关行为。
- 在没有迁移、兼容或回滚说明的情况下改变持久化数据结构。
- 在没有 SSoT sync 的情况下改变长期事实。

## 边界证据

每次 review 至少检查这些证据：

- `requirements.md` 中是否有范围和非目标。
- `design.md` 中是否有写入范围和契约影响。
- `tasks.md` 中是否有任务依赖和边界标注。
- `changed-files.md` 是否和设计写入范围一致。
- `verification/report.md` 是否覆盖被影响的边界。
