# 认证、授权和速率限制

本参考用于 API 的身份识别、权限控制、租户隔离、审计和限流设计。安全不是 spec 的附录，而是接口契约的一部分。

## 认证方式选择

| 方式 | 适用场景 | 主要关注 |
|---|---|---|
| Bearer Token | 服务端 API、移动端、SPA 后端 | 过期、刷新、撤销 |
| OAuth2 / OIDC | 第三方授权、开放平台 | scope、redirect、consent |
| API Key | 服务间或开发者平台的简单鉴权 | 泄露、轮换、配额 |
| mTLS | 高安全 B2B 或内部服务 | 证书签发和轮换 |
| Session Cookie | 传统 Web | CSRF、SameSite、会话失效 |

设计时必须说明：

- 谁是主体。
- 凭证从哪里获得。
- 凭证有效期。
- 刷新和撤销。
- 轮换机制。
- 失效后的响应。

## 授权模型

授权至少要回答：

- 按角色、scope、ABAC 还是资源 owner 判断。
- 是否存在租户隔离。
- 是否存在资源级权限。
- 是否存在操作级权限。
- 字段级脱敏是否因权限变化。
- 系统管理员是否可绕过普通权限。

推荐把每个 operation 的授权要求写成表：

| 操作 | 认证 | 角色 / scope | 资源条件 | 审计 |
|---|---|---|---|---|
| `GET /users/{id}` | 必须 | `user:read` | 同租户 | 是 |
| `PATCH /users/{id}` | 必须 | `user:write` | owner 或 admin | 是 |

## `401` 与 `403`

| 场景 | 返回 |
|---|---|
| 未登录、token 缺失 | `401` |
| token 失效、签名错误 | `401` |
| 已登录但无权限 | `403` |
| 资源存在但不应暴露 | 可返回 `404` |

错误响应必须和 `error-handling.md` 保持一致。

## 多租户隔离

多租户系统必须明确：

- tenant id 来源。
- tenant id 是否允许客户端传入。
- 查询是否自动附加 tenant 过滤。
- 跨租户访问如何拒绝。
- 后台运维是否有跨租户能力。
- 审计日志是否记录 tenant。

任何“由客户端传 tenant_id 并直接信任”的设计都需要高度警惕。

## 敏感信息

必须说明：

- 哪些字段需要脱敏。
- 哪些字段不得进入日志。
- 哪些字段只可写不可读。
- PII 如何在响应、日志、导出中处理。
- 密钥、token、签名材料是否永不回显。

## 速率限制

速率限制需要写清：

- 限制对象：用户、租户、IP、token、endpoint 或全局。
- 计数窗口。
- 默认限制和突发限制。
- 是否对不同 endpoint 分级。
- 超限响应。
- `Retry-After` 或等价重试建议。
- 是否对认证失败、登录、验证码等敏感接口单独限流。

推荐响应头：

- `RateLimit-Limit`
- `RateLimit-Remaining`
- `RateLimit-Reset`
- `Retry-After`

## 审计和合规

安全敏感 API 还必须说明：

- 审计日志字段。
- 谁执行了什么动作。
- 作用于哪个资源。
- 操作是否成功。
- 来源 IP / client id。
- request id / trace id。
- 是否需要不可抵赖记录。

## 验证要求

verification 应优先包含：

- 无凭证请求。
- 过期凭证。
- 权限不足。
- 越权访问。
- 跨租户访问。
- 限流触发。
- 敏感字段脱敏。
- 审计日志记录。
- token 撤销或轮换后的行为。

## Review Checklist

- 认证方式是否与场景匹配。
- token / key 生命周期是否明确。
- 授权规则是否到 operation、资源、字段级别。
- `401` / `403` / `404` 语义是否清楚。
- 多租户隔离是否可执行。
- 敏感字段是否有脱敏和日志策略。
- 限流是否有维度、窗口、头部和重试建议。
- 是否有权限回归和越权测试。
