# 分页、排序和过滤

所有集合接口必须选择分页策略，除非契约明确说明结果数量有硬上限。分页不是性能细节，而是调用方体验和系统稳定性的契约。

## 策略选择

| 策略 | 适用场景 | 优点 | 风险 |
|---|---|---|---|
| `offset` / `limit` | 小数据集、后台管理页、需要跳页 | 简单直观 | 大 offset 慢，数据变化时可能重复或遗漏 |
| `page` / `per_page` | 传统页面型列表 | 便于 UI 展示 | 本质仍是 offset，不适合实时大数据 |
| `cursor` | feed、时间线、实时数据、大集合 | 稳定、性能好 | 不能随机跳页，cursor 需要设计 |
| `keyset` | 大表、高性能、有稳定排序键 | 性能最强 | 对排序和过滤约束更严格 |

默认建议：对外 API 和大集合优先 cursor；内部后台小列表可以 offset。

## Cursor 分页契约

cursor 分页应说明：

- `limit` 默认值和最大值。
- `cursor` 是否 opaque，调用方不得解析。
- 排序字段和稳定 tie-breaker。
- 响应是否包含 `next_cursor`、`prev_cursor`、`has_more`。
- 最后一页如何表达。
- cursor 过期、非法、与过滤条件不匹配时返回什么错误。

推荐响应形态：

```json
{
  "data": [],
  "pagination": {
    "next_cursor": null,
    "has_more": false,
    "limit": 20
  }
}
```

## Offset 分页契约

offset 分页应说明：

- `offset` 最小值。
- `limit` 默认值和最大值。
- 是否返回 `total`。
- `total` 是精确值、估算值，还是可选计算。
- offset 越界时返回空列表还是错误。

如果 total 成本很高，不要默认强制返回；可用 `include_total=true` 或单独统计接口。

## 排序

排序字段必须白名单化。

| 需求 | 规则 |
|---|---|
| 默认排序 | 必须稳定，例如 `created_at desc, id desc` |
| 多字段排序 | 明确优先级，例如 `sort=-created_at,name` |
| cursor 排序 | cursor 必须绑定排序条件 |
| 不支持排序 | 明确写出原因和默认顺序 |

不要让调用方按未索引、敏感或不稳定字段排序。

## 过滤

过滤条件必须写清：

- 字段类型。
- 允许值或范围。
- 大小写是否敏感。
- 多个条件之间是 AND 还是 OR。
- 空值和缺省值语义。
- 过滤发生在分页之前还是之后。
- 不支持的组合如何报错。

复杂过滤如果已经难以用 query 表达，应建模为搜索资源或专用查询对象。

## 边界行为

必须定义：

- 空集合返回 `200` 和空数组，而不是 `404`。
- 最后一页如何表达。
- 非法 cursor 如何报错。
- limit 超过最大值是裁剪还是报错。
- 过滤后没有结果如何返回。
- 数据在翻页过程中新增或删除时是否保证一致性。

## Review Checklist

- 所有集合接口是否分页或有明确上限。
- 是否选择了适合数据规模和体验的分页策略。
- limit 默认值和最大值是否明确。
- 排序是否稳定且字段白名单化。
- total 是否有成本说明。
- cursor 是否 opaque。
- 空结果、最后一页、非法参数是否定义清楚。
