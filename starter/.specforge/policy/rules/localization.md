# 中文优先规则

SpecForge 的默认读者是中文工程协作场景。除代码标识符、命令、文件名、协议关键字和引用原文外，面向人的说明应优先使用中文。

## 适用范围

- `.specforge/` 中的规则、技能、模板说明。
- `.specforge/workspace/knowledge/` 中的长期知识。
- `.specforge/workspace/changes/` 中的变更产物。
- `docs/` 中的研究、架构和使用文档。

## 保留英文的情况

- CLI 命令和参数，例如 `node .specforge/execution/tools/validate-structure.mjs`。
- 文件名、路径、包名、类名、函数名。
- 约定状态值，例如 `APPROVED`、`PENDING`、`NO-GO`。
- 外部项目的术语首次出现时可保留英文并给出中文解释。
- 标准名称、协议名、产品名，例如 OpenAPI、OWASP ASVS、NIST SSDF。

## 写作要求

- 少写泛泛的价值判断，多写机制、边界、输入、输出、完成条件。
- 同一概念保持同一译名，例如 artifact 统一写作“产物”，gate 统一写作“门禁”。
- 研究文档可以保留出处链接，但结论必须落到 SpecForge 的可执行改进上。
- 面向 Agent 的句子应短、直接、可执行。
- 不使用“最好”“尽量”“更稳”这类没有判断标准的词，除非后面写清判断条件。
- 少写“这一篇、上一篇、下一篇、第一次接触”这类依赖阅读顺序的表述。
- 模板文字应能独立理解，不依赖某篇示例文档。
- 优先使用直接句式，减少绕弯表达。
- 同一段只表达一个主要结论，必要时拆段或改成表格。
- 命令、状态值、路径和术语要有稳定写法，避免同义反复。
- 面向开发者的说明优先写“怎么判断、怎么执行、什么算完成”，少写营销式表达。

## 推荐术语

| English | 中文 |
|---|---|
| artifact | 产物 |
| gate | 门禁 |
| workflow | 工作流 |
| change | 变更 |
| requirement | 需求 |
| design | 设计 |
| task | 任务 |
| verification | 验证 |
| evidence | 证据 |
| archive | 归档 |
| Single Source of Truth / SSoT | 唯一事实源 |
| steering | 持久上下文 |

## 文档风格

- 规则文档使用“必须、应该、可以、不得”表达约束强度。
- 研究文档先给结论，再给证据和链接。
- 模板文档保留清晰标题和占位说明，但不要写成教程。
- 周报、计划、项目记录使用简洁表格或条目，不写长篇背景。
- 对外 README 可以保留英文命令和 npm/GitHub 生态术语。
- 面向机器和 Agent 的规则优先使用稳定结构：触发条件、必做项、反模式、证据。
- 面向协作的说明优先使用具体动作，避免“注意”“建议关注”这类无落点表达。

## 引用规则

- 引用外部规范时写链接和适用结论，不复制大段原文。
- 如果规范版本重要，写明版本或访问日期。
- 如果只是借鉴思想，使用“参考”而不是“遵循”。

## 参考来源

- Microsoft 的 developer content 指南强调清晰、结构化和面向任务的技术表达。
- Microsoft Localization Style Guides 提供中文本地化与术语一致性的参考。
