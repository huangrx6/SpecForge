# PRD Playbook

本文件是产品需求文档能力包的执行总纲。它合并原 `foundations/` 和 `transforms/` 的职责：阶段边界、决策状态、PRD 语言、假设台账，以及 brief / brainstorm / product discovery / research 到 PRD 的转译规则。

## Product Decision Boundary

产品需求文档是产品决策文档，不是需求规格、界面设计、技术设计或任务计划。

产品需求文档可以决定：

- 为什么做。
- 给谁做。
- 解决什么问题。
- 第一版最小可行版本做什么。
- 第一版不做什么。
- 用户价值和业务目标。
- 成功指标。
- 候选功能如何取舍。
- 哪些风险需要下游处理。
- 是否进入需求阶段。

产品需求文档不可以决定：

- 接口字段、数据库表、组件拆分、技术栈细节。
- 测试命令、任务排期、最终验收标准编号。
- 具体实现路径。

边界修正：

| 越界信号 | 修正 |
|---|---|
| PRD 写需求 / 验收编号 | 改成用户故事与验收种子，交给需求阶段转译 |
| PRD 写接口 / 数据库 / SDK | 移到给技术设计阶段的备注或依赖决策 |
| PRD 写组件 / 颜色 / 布局 | 移到给界面设计阶段的备注 |
| PRD 写测试命令 | 移到验证阶段交接 |
| Agent 建议写成 MVP | 改成候选、授权默认或待确认 |

## Decision Status

顶层 `decision_status` 只表达整个产品需求文档是否可进入需求阶段。

| 状态 | 含义 | 要求动作 |
|---|---|---|
| `draft` | PRD 正在生成 | 不进入需求阶段 |
| `needs-decision` | 需要用户或业务负责人确认 | 停止并提问 |
| `research-needed` | 缺事实、数据、竞品、合规或 AI 能力证据 | 转产品发现或预研 |
| `approved-for-requirements` | 可进入需求阶段 | 运行指令检查并路由 |
| `blocked-by-conflict` | 上游输入冲突 | 列冲突并等待决策 |

进入需求阶段的最小条件：

- 目标用户明确。
- 核心问题明确。
- 最小可行版本范围明确。
- 非目标明确。
- 成功标准至少有一个可观察指标。
- 高影响未决问题已清零，或有明确负责人和需要时间。
- 交接给需求阶段中有需求种子。

`delegated-default` 不是顶层状态，只能作为具体 MVP 项、假设项、范围项或开放问题的确认类型。

| 确认类型 | 含义 | 可进入 MVP |
|---|---|---|
| `user-confirmed` | 用户明确确认 | 是 |
| `delegated-default` | 用户授权 agent 按默认建议推进 | 是，但必须写风险、回退点和复核触发 |
| `agent-recommendation` | Agent 建议 | 否，只能作为候选 |
| `pending` | 未确认 | 否 |

决策状态输出：

```md
决策状态:
- 状态:
- 原因:
- 是否可进入需求阶段: 是 / 否
- 风险备注:
- 回退点:
- 所需决策:
```

## PRD Language

PRD 写产品决策语言，不写工程规格语言。

推荐写法：

| 内容 | 写法 |
|---|---|
| 问题 | `目标用户在 <场景> 中无法 <完成目标>，导致 <代价>` |
| 目标结果 | `本版本希望让 <用户> 能够 <结果>，用 <指标> 观察` |
| MVP | `MVP 包含 <能力>，因为它直接支撑 <用户价值 / 业务目标>` |
| 非目标 | `本期不做 <能力>，避免 <风险 / 范围膨胀>；后续触发条件是 <条件>` |
| 成功标准 | `用 <可观察指标> 判断是否改善 <问题>` |
| 下游交接 | `需求阶段需要把 <种子> 转成可测试行为` |

禁止写法：

- “系统必须使用 Redis / Vue / GraphQL / 某 SDK”。
- “按钮使用红色 badge / shadcn Table / 三列布局”。
- “REQ-001 / AC-001”。
- “执行 npm test / playwright 命令”。
- “智能、完善、高效、易用”但没有指标或观察证据。
- “按最佳实践实现”。

PRD 可以写验收种子，但不能写最终验收标准：

```md
验收种子:
- 客户经理打开提醒页面时，应能看到即将到期客户、到期时间、剩余天数和联系状态。
```

## Assumption Ledger

PRD 可以记录假设，但不能把假设伪装成已确认事实。

| 类型 | 含义 | PRD 处理 |
|---|---|---|
| `confirmed` | 用户、上游 PRD、预研或知识库已确认 | 可作为 MVP、指标和非目标依据 |
| `delegated-default` | 用户授权 agent 按默认建议推进 | 可进入 PRD，但要写风险备注和回退点 |
| `likely` | 有弱证据或合理推断 | 只能写假设，不作为已批准 MVP 的唯一依据 |
| `unclear` | 无足够证据 | 写开放问题或标记为需要预研 |
| `conflict` | 上游材料互相冲突 | 写 `blocked-by-conflict` |

台账格式：

```md
| 假设 / 事实 | 类型 | 证据 | 影响 | 负责人 | 复核触发条件 |
|---|---|---|---|---|---|
```

规则：

- 高影响假设不能隐藏在正文里。
- 影响 MVP、数据权限、AI 质量、合规或成本的假设必须有负责人。
- `unclear` 不能进入 `approved-for-requirements`，除非它不影响 MVP 和下游交接。
- `delegated-default` 必须写明回退点。

## Source Transforms

### Brief To PRD

| `brief.md` 字段 | PRD 位置 | 处理 |
|---|---|---|
| 用户目标 | 产品决策摘要 / 背景 | 转成问题和期望结果 |
| 推荐流程 | PRD 控制 | 写来源流程 |
| PRD 决策 | PRD 控制 | 决定是否需要 PRD 和输出深度 |
| Brainstorm 决策 | 范围与 MVP | 只采用用户已确认或授权默认的内容 |
| 范围内 | 候选功能池 / 范围 | 转成候选功能或 MVP |
| 范围外 | 非目标 | 保留原因 |
| 关键未知 | 开放问题 | 高影响未知阻断 |
| 影响面标记 | 下游交接 | 触发 UI、技术、数据或安全交接 |

规则：

- brief 里没有确认的内容不能写成已批准 PRD。
- Agent 建议只能进入候选，不进 MVP。
- 如果目标用户、核心问题、成功标准缺失，停止并提问。
- 如果 brief 和 brainstorm 冲突，以用户确认记录为准；冲突写入开放问题。

### Brainstorm To PRD

| Brainstorm 内容 | PRD 位置 |
|---|---|
| 用户确认记录 | 范围与 MVP 决策 |
| 明确延后 / 不做 | 非目标 / 路线图 |
| 推荐方案 | 候选功能池，不能直接变 MVP |
| 方案评估矩阵 | 范围决策理由 |
| 当前事实与研究证据 | 背景 / 风险 |
| 下一步路由 | 下游交接 |

确认类型映射：

| Brainstorm 确认类型 | PRD 处理 |
|---|---|
| `user-confirmed` | 可进入 MVP、非目标或成功标准 |
| `delegated-default` | 可进入 MVP，但写风险备注和回退点 |
| `agent-recommendation` | 进入候选功能池 |
| `pending` | 进入开放问题 |

禁止：

- 不把 Agent recommendation 写成用户选择。
- 不把待确认问题包装成默认假设。
- 不复制完整 brainstorm 过程，只提取决策、依据和未决问题。
- 不把方案评估矩阵里的 `adopt` 直接等同于用户已确认。

### Product Discovery To PRD

| 产品发现内容 | PRD 位置 |
|---|---|
| 期望结果 | 产品决策摘要 / 指标 |
| 机会 | 问题 / 背景 / 候选功能池 |
| 方案候选 | 候选功能池 |
| `confirmation_status=user-confirmed-mvp` | 范围与 MVP 决策 |
| `confirmation_status=delegated-default` | 范围与 MVP 决策，必须写风险和回退点 |
| `confirmation_status=mvp-recommended` | 候选功能池 / 开放问题，不能直接进入 MVP |
| 实验 | 风险 / 路线图 / 验证 |
| 优先级评分 | 范围与 MVP 决策理由 |
| 证据缺口 | 开放问题 / 需要预研 |

规则：

- 机会不是功能，不能直接写成 MVP。
- 方案候选不是已确认范围，必须经过用户确认或授权默认。
- `mvp-recommended` 不能直接写入 PRD Decision JSON 的 `mvp[]`。
- `delegated-default` 转入 PRD 时，写入具体 MVP 项的 `confirmation_type=delegated-default`，并补齐 `risk`、`handoff` 和回退点。
- 实验不等于发布计划，只能作为验证或预研交接。

### Research To PRD

预研输入只转成产品决策证据、风险、约束、指标或开放问题；不直接写技术方案。

| 预研内容 | PRD 位置 | 处理 |
|---|---|---|
| 已确认事实 | 背景 / 风险 / 快照 | 写事实、来源和影响 |
| 不清楚的事实 | 开放问题 | 写负责人和需要时间 |
| 服务商限制 | AI、数据与合规快照 | 写成本、延迟、限流或交付风险 |
| 竞品事实 | 候选功能池 / 风险 | 写参考，不当作必须照抄 |
| 合规 / 安全事实 | 风险 / 非目标 / 下游交接 | 写数据、安全、人工复核或需要预研 |

规则：

- 当前事实不足以决定范围或指标时，`decision_status = research-needed`。
- 技术事实只在 PRD 中写产品影响，例如成本、延迟、可用性、合规限制。
- PRD 不把预研验证的实现细节变成 MVP。
- 引用事实时记录来源文件和结论，不复制长篇预研内容。
