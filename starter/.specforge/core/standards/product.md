# 产品与需求标准

本标准回答：需求如何澄清，PRD 何时需要，requirements 怎么写才可实现、可测试、可验收。

## 需求分层

| 产物 | 作用 | 不做什么 |
|---|---|---|
| `brief.md` | 保留原始请求、分类 workflow、记录范围和 PRD 决策 | 不展开完整需求 |
| `prd.md` | 产品问题、用户、候选能力、MVP、指标、路线图 | 不写接口和实现细节 |
| `requirements.md` | 可测试行为、用户故事、验收标准、边界、异常 | 不做技术选型 |

## PRD 决策

需要 PRD 的情况：

- 用户只给出高层想法，还没有清楚功能边界。
- 新增产品能力、AI 功能、后台工具、全栈应用、跨角色流程。
- 需要比较多个功能候选、MVP 组合、成功指标或上线阶段。

可以跳过 PRD 的情况：

- 明确 bugfix、issue、低风险配置、文案或行为很小的 lite change。
- 需求已经包含目标用户、范围、验收标准和非目标。

跳过 PRD 时，在 `brief.md#PRD 决策` 写清理由。

## 访谈方式

访谈不使用固定问卷，而使用问题预算：

1. 先复述当前理解。
2. 列出 5 个候选方向或功能点，让用户选择、删减、补充。
3. 对阻断决策追问；对非阻断细节写默认假设。
4. 每轮问题尽量少，优先问会影响范围、角色、数据、安全、验收的问题。
5. 如果用户已经明确决策，不重复追问。

## Requirements 必须包含

- 目标与非目标。
- 角色和权限差异。
- 用户故事或行为清单。
- 正常路径、异常路径、边界值。
- 数据输入、输出、格式和约束。
- 验收标准：可执行、可观察、可失败。
- 影响面 flags：UI、API、DB、权限、配置、任务、AI、集成、测试。
- 未决问题：只保留真正阻断下一步的 `[NEEDS CLARIFICATION]`。

## 可测试写法

优先使用：

```text
Given <前置条件>
When <用户动作或系统事件>
Then <可观察结果>
```

验收标准不得只写“体验好”“性能好”“支持上传”。必须补充可判断条件，例如文件类型、大小、并发、错误反馈、重试策略、日志或权限结果。

## 功能候选与 MVP

产品型需求必须先形成候选池，再确认 MVP：

- 必选：没有它目标不成立。
- 可选：有价值但可以延后。
- 明确不做：避免实现阶段范围蔓延。

候选池来自用户请求、类似系统、业务约束和风险分析，但最终必须落成用户可确认的选择。

## 阻断项

- 需求不可测试。
- 角色、数据、权限或输出边界不清。
- PRD 标记 required 但缺失或未批准。
- 产品型需求没有候选池、MVP 选择或默认假设。
- requirements 与 brief / PRD 目标不一致。
