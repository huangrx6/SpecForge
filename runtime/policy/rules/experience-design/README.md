# 体验设计规则

本规则用于页面、应用、后台、前端组件和全栈产品的 UX / UI 设计。它要求 design 不只写技术结构，还要写清用户如何使用、页面如何组织、视觉和交互如何落地。

## 什么时候必须启用

- 新增或大改用户可见页面。
- 新增后台、仪表盘、编辑器、内容管理、工作台或多步骤流程。
- 用户提到页面、设计、主题、线稿、原型、交互或视觉风格。
- 实现需要选择组件库、编辑器、图表、表单、拖拽、富文本或 Markdown 编辑体验。

## 必含内容

### 页面地图

列出页面、路径、主要目标、入口和跳转关系。

| 页面 | 路径 | 用户目标 | 入口 | 主要状态 |
|---|---|---|---|---|

### 用户流程

至少覆盖主成功路径和一个失败 / 空状态路径。可以使用 Mermaid。

### 线稿或原型

根据工具能力选择一种：

- 简单需求：在 `design.md` 中用 ASCII / Markdown 描述页面区块。
- 复杂或视觉敏感需求：使用 Pencil、Figma 或其他可用设计工具生成原型，并在 `design.md` 链接证据。
- 无法使用设计工具时：明确写出原因，并给出足够详细的页面结构、区块层级和状态矩阵。

### 视觉方向

必须明确：

- 主题关键词。
- 主色、辅助色、背景色、文本色。
- 字体倾向。
- 间距和布局密度。
- 卡片、表格、表单、导航和按钮风格。
- 暗色模式是否包含在本次范围。

### 交互状态

至少覆盖：

- loading
- empty
- error
- success
- disabled
- destructive confirmation
- mobile layout

## 技术选择

涉及 UI 技术时，design 必须说明：

- 使用哪个前端框架 / 组件库 / 样式方案。
- 编辑器、Markdown、富文本、图表或复杂交互使用什么库。
- 为什么选它，为什么不选备选方案。
- 与 `.specforge/policy/tech-profiles/` 中哪个 profile 对齐。

## Spec Review 阻断条件

- 有用户可见页面但没有页面地图。
- 有新 UI 但没有视觉方向和交互状态。
- 有编辑器、图表、富文本、拖拽等复杂控件但没有技术选择和备选方案。
- 用户没有确认关键体验选择，却进入 implementation。
