# 产品发现规则

本规则用于把“我要做一个产品 / 页面 / 全栈应用 / 工具”从一句话扩展成可选择、可确认、可拆分的需求空间。它的目标不是拖慢流程，而是防止 Agent 过早把模糊想法压成最小 CRUD。

## 什么时候必须启用

- 用户提出新产品、页面、后台、全栈应用、工具、仪表盘或复杂功能。
- 用户只给出高层目标，例如“做个人博客”“做 CRM”“做一个管理系统”。
- 需求涉及多个角色、多个页面、内容管理、权限、数据模型或用户路径。

## 核心动作

1. 先复述用户目标和已确认约束。
2. 生成候选功能池，按 `MVP / 可选增强 / 后续版本` 分组。
3. 标出每个候选功能的用户价值、复杂度、风险和依赖。
4. 给出推荐 MVP 组合，但必须让用户确认、删减或补充。
5. 对缺少关键事实的问题列出澄清项；复杂需求不得只问技术栈。
6. 当候选功能超过一个独立交付目标时，建议拆 roadmap 或多 change。

## 功能候选表

| 功能 | 建议阶段 | 用户价值 | 复杂度 | 风险 / 依赖 | 默认建议 |
|---|---|---|---|---|---|
| 示例功能 | MVP / 后续 | 为什么需要 | S/M/L | 权限、数据、部署等 | include / optional / defer |

## 必问问题

按任务类型选择，不要机械全问：

- 目标用户是谁？个人自用、团队内部、公开用户还是多角色系统？
- 第一版成功标准是什么？用户看到什么才算完成？
- 哪些功能必须第一版有，哪些可以后续再做？
- 数据是否需要导入、导出、备份或迁移？
- 是否会公网部署？是否需要认证、权限、审计或安全边界？
- 是否有品牌、主题、视觉风格或交互偏好？
- 是否有技术栈、部署平台、数据库或第三方服务约束？

## 停止条件

- 用户尚未确认 MVP 功能组合。
- 候选功能明显跨多个 change，但没有拆分计划。
- 权限、安全、数据迁移或公网部署边界不清。
- UI / 体验类工作没有视觉方向或页面范围。

## 产物要求

`00-intake/brief.md` 和 `01-spec/requirements.md` 应留下：

- 已确认的 MVP 功能。
- 明确延后的功能。
- 用户做出的选择。
- Agent 的默认假设。
- 仍需澄清的问题。
