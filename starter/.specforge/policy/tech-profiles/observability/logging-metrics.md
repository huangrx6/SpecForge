# 日志、链路与监控 (Observability)

## 1. 体系全景 (The Three Pillars)
- 可观测性必须同时涵盖三大支柱：**结构化日志 (Logs)**、**全链路追踪 (Traces)**、**指标监控 (Metrics)**。它们共同决定了系统在不可预知状态下的排障与生存能力。

## 2. 日志规范 (Logging Standard)
- **格式一致性**：开发环境输出人友好的着色文本；生产环境**必须输出纯净的 JSON 字符串** (Structured Logging)。
- **前台监控**：
  - 必须接入专门的异常报警平台 (如 Sentry, Datadog RUM)，拦截并收集浏览器环境发出的崩溃报错、控制台异常及未捕获的 Promise 错误。
  - 重大交互应上报行为日志 (Action Logs) 以供审计溯源。
- **后端红线与隔离**：
  - **TraceID 强绑定**：每逢请求入站，必须立刻生成全局唯一的 `TraceID`。这一标识必须伴随请求穿越各个函数切面、MDC 及整个微服务网格生态群，甚至打印入每一条日志内。
  - **敏感信息的屠宰场 (Data Sanitization)**：严禁打印用户密码、完整身份证号、银行卡明文、Token/Session 签名进入日志，这极度违反合规要求。

## 3. 分级告警与响应机制 (Alerting & Levels)
- 日志等级：
  - `DEBUG`：仅用于线下沙盒探测，严禁流入生产大盘。
  - `INFO`：系统的脉搏。业务核心状态转折点 (如下单、支付回调成功)。
  - `WARN`：亚健康状态，如网络请求偶尔的超时重试，但最终兜底成功。
  - `ERROR`：请求崩溃，业务死锁。一旦抛出必须无条件触发人工值守报警网。
  - `FATAL`：基础设施毁灭级灾难，如数据库离线，服务直接拉闸。
- 报警通道应按级别智能降噪，防止因为过多无用报警产生“狼来了”效应导致运维疲劳。

## 4. 指标与仪表盘 (Metrics)
- 核心服务必须开放 `/metrics` 端点以供 Prometheus 抓取。
- 基于 USE 原则监测资源 (Utilization 饱和度、Errors、资源耗用)。
- 基于 RED 原则监测 API (Rate 请求速率、Errors 错误数、Duration 响应耗时)。

## 5. Design 必填问题

- 本次 change 增加哪些关键用户动作、后台任务或外部调用？
- 哪些失败需要告警，哪些只记录为可排查日志？
- trace id / request id 如何从入口传到数据库、队列和下游服务？
- 需要哪些业务指标：创建量、发布量、支付成功率、AI 调用耗时、错误率？
- 验证阶段如何证明日志、指标或 trace 已产生？

## 6. Spec Review 检查项

- 新增关键链路有结构化日志字段，不只写自然语言。
- 错误日志带 request id / trace id。
- 告警有阈值和降噪策略，不把所有 warn 都推给人工。
- 敏感字段在日志前被脱敏。
- verification 能留下可观测性证据。
