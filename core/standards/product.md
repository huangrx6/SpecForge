# 产品与需求标准

本标准回答：需求如何澄清，产品需求文档何时需要，需求规格怎么写才可实现、可测试、可验收。

## 需求分层

| 产物 | 作用 | 不做什么 |
|---|---|---|
| `brief.md` | 保留原始请求、分类工作流、记录范围和产品需求文档决策 | 不展开完整需求 |
| `brainstorm.md` | 记录用户参与式发散、优秀案例侦察、当前事实、方案对比、取舍和已确认选择 | 不替用户拍板，不写最终规格，不复制外部案例 |
| `prd.md` | 产品问题、用户、候选能力、最小可行版本、指标、路线图 | 不写接口和实现细节 |
| `requirements.md` | 可测试行为、用户故事、验收标准、边界、异常 | 不做技术选型 |

## Brainstorm 决策

需要 brainstorm 的情况：

- 用户想法仍模糊，或明确要求"先讨论 / 头脑风暴 / 帮我想想"。
- 产品型功能、页面体验、AI 能力、多角色流程、审批/权限/数据生命周期尚未确认核心方向。
- 用户提供优秀网站、模板站、竞品、截图或要求“高级一点 / 不要模板化 / 多找案例 / 多探讨方向”。
- 产品需求文档、需求规格、界面设计或技术设计中存在会改变范围、体验或架构的未决选择。
- 技术路线、依赖版本、模型能力、外部服务、安全策略或部署成本需要用户取舍。

可以跳过 brainstorm 的情况：

- 用户已经给出明确方案、范围、非目标和验收标准。
- bugfix、issue、低风险 lite change 或纯 refactor 没有产品/体验/技术路线取舍。
- 只是补全文案、格式或已批准 spec 的机械拆解。

Brainstorm 是 graph 外阶段；需要时写入 `00-intake/brainstorm.md` 并同步 `brief.md`，不强制每个 work item 都经过。

## 产品需求文档决策

需要产品需求文档的情况：

- 用户只给出高层想法，还没有清楚功能边界。
- 新增产品能力、AI 功能、后台工具、全栈应用、跨角色流程。
- 需要比较多个功能候选、最小可行版本组合、成功指标或上线阶段。

可以跳过产品需求文档的情况：

- 明确 bugfix、issue、低风险配置、文案或行为很小的 lite change。
- 需求已经包含目标用户、范围、验收标准和非目标。

跳过产品需求文档时，在 `brief.md#产品需求文档决策` 写清理由。

## 访谈方式

访谈不使用固定问卷，而使用问题预算：

1. 先复述当前理解。
2. 列出 5 个候选方向或功能点，让用户选择、删减、补充。
3. 对阻断决策追问；对非阻断细节写默认假设。
4. 每轮问题尽量少，优先问会影响范围、角色、数据、安全、验收的问题。
5. 如果用户已经明确决策，不重复追问。

## 需求规格必须包含

- 目标与非目标。
- 角色和权限差异。
- 用户故事或行为清单。
- 正常路径、异常路径、边界值。
- 数据输入、输出、格式和约束。
- 验收标准：可执行、可观察、可失败。
- 影响面 flags：UI、API、DB、权限、配置、任务、AI、集成、测试。
- 未决问题：只保留真正阻断下一步的 `[NEEDS CLARIFICATION]`。

## 可测试写法

优先使用：

```text
Given <前置条件>
When <用户动作或系统事件>
Then <可观察结果>
```

验收标准不得只写"体验好""性能好""支持上传"。必须补充可判断条件，例如文件类型、大小、并发、错误反馈、重试策略、日志或权限结果。

## 功能候选与最小可行版本

产品型需求必须先形成候选池，再确认最小可行版本：

- 必选：没有它目标不成立。
- 可选：有价值但可以延后。
- 明确不做：避免实现阶段范围蔓延。

候选池来自用户请求、类似系统、优秀案例机制、业务约束和风险分析，但最终必须落成用户可确认的选择。优秀案例只能提取可迁移机制、不能照搬品牌资产、文案、专有交互或代码；案例影响体验 / 产品方向时，必须在 `brainstorm.md#优秀案例与机制拆解` 记录来源、访问日期、可迁移机制、不能照搬点和成本风险。

## 用户画像（Persona）

产品型需求必须识别目标用户画像。画像基于真实用户调研数据，不允许基于假设或人口统计学臆测。

### 画像定义要求

- 限制在 3-5 个主要画像。
- 每个画像必须包含：目标、痛点、行为模式和使用场景。
- 画像随用户调研数据的积累持续更新。

### 画像模板

```markdown
## [画像名称]
**年龄:** [年龄] | **职业:** [职称] | **场景:** [使用场景]

### 目标
- [与产品相关的主要目标]
- [次要目标]

### 痛点
- [对当前方案的不满]
- [未被满足的需求]

### 行为模式
- [当前如何解决问题]
- [技术熟练程度和偏好]
```

### 画像反模式

- ❌ 仅有人口统计学信息的画像（"25-35 岁白领"不是画像）。
- ❌ 理想化画像（基于期望而非数据）。
- ❌ 过多画像（超过 5 个说明未做聚焦）。
- ❌ 长期不更新的陈旧画像。

## 用户调研访谈（UX Research）

### 访谈规划

- 在打开设计工具之前先做调研。
- 编写 8-12 个开放式问题的讨论指南。
- 每轮招募 5-8 名参与者获取定性洞察。
- 每次访谈安排 45-60 分钟（30 分钟访谈 + 缓冲）。

### 访谈技巧

- 用简单的暖场问题建立信任。
- 询问过去的行为，而非假设性的未来行为。
- 使用"告诉我你上次做 XX 的经历"的框架。
- 追问"为什么？"和"能展示给我看吗？"。
- 提问后保持沉默，让参与者填充空间。

### 访谈问题质量

| ✅ 好问题 | ❌ 坏问题 |
|---|---|
| "带我回顾一下你上次做[任务]的过程。" | "你难道不觉得这个功能有用吗？"（引导） |
| "那次体验中最困难的部分是什么？" | "你会用一个能做 X 的产品吗？"（假设性） |
| "在找到这个方案之前你试过什么？" | "你喜欢这个设计吗？"（意见而非行为） |

### 调研综合

1. 24 小时内趁记忆清晰时进行复盘。
2. 将关键观察提取为独立数据点。
3. 使用亲和图法（Affinity Mapping）将观察聚类为主题。
4. 识别跨参与者的模式。
5. 按频率和影响力对洞察排优先级。
6. 创建与具体发现挂钩的可执行建议。

## "如何能"（How Might We）问题框架

定义问题时使用"如何能"框架，将痛点转化为设计机会：

- `HMW [为目标用户] [解决痛点] [使其达成目标]?`
- 问题必须足够具体可行动，又足够开放容纳多个方案。
- 每个 HMW 问题都应对应一个已识别的用户画像。

## 阻断项

- 需求不可测试。
- 角色、数据、权限或输出边界不清。
- 产品需求文档标记需要但缺失或未批准。
- 产品型需求没有候选池、最小可行版本选择或默认假设。
- 需求规格与简报 / 产品需求文档目标不一致。
- 产品型需求未识别目标用户画像，或画像仅基于假设而非调研。
