# SQLite Embedded Database

## 适用 / 不适用

适用：

- 桌面应用、移动应用、CLI、本地优先工具、插件、边缘节点或单机内部工具。
- 需要零运维、单文件部署、快速测试夹具或本地缓存。
- 数据主要由单个进程或低并发写入者访问。

不适用：

- 多应用实例同时写入同一个数据库文件。
- 高并发服务端 OLTP、复杂权限隔离、跨机器共享写入。
- 需要独立数据库运维能力、只读副本、集中审计或细粒度访问控制。

## 默认组合

| 能力 | 默认建议 | 说明 |
|---|---|---|
| 存储形态 | 单文件数据库 | 文件位置、权限和备份策略是设计的一部分 |
| 事务 | 显式事务 | 批量写入和一致性变更必须包事务 |
| 外键 | `PRAGMA foreign_keys = ON` | SQLite 需要连接级启用外键约束 |
| 并发 | WAL 模式按需启用 | WAL 改善读写并发，但仍不是多写入者数据库 |
| 类型 | 优先 STRICT table | 减少动态类型带来的数据污染 |
| 迁移 | 版本表 + 增量 SQL | 每次启动或发布时可检查 schema version |

## Schema 与约束

- 明确数据库文件路径、创建时机、目录权限和生命周期。
- 新表优先评估 `STRICT`，减少类型漂移。
- 主键、唯一约束、外键、检查约束要显式写入 schema。
- 时间建议保存为 UTC ISO 字符串或 Unix epoch，项目内保持一致。
- 大文本、图片、附件通常不直接塞入主库；评估文件系统或对象存储，并保存引用。

## 索引、事务与并发

- 高频查询要有索引；用 `EXPLAIN QUERY PLAN` 验证关键查询。
- 批量写入必须使用事务，避免逐条 autocommit。
- WAL 模式适合读多写少或读写交错场景；需要说明 checkpoint 策略和文件清理。
- 多进程访问要说明锁等待、busy timeout 和失败重试策略。
- 单机数据库损坏、磁盘满、权限变化、路径迁移都要作为失败模式处理。

## 迁移、备份与同步

- 使用 `schema_version` 或专用 migrations 表追踪结构版本。
- 迁移脚本必须可重复检测当前版本，失败时不能留下半迁移状态。
- 备份应优先使用 SQLite backup API 或应用停写后的文件复制，不要在写入中随意复制裸文件。
- 需要云同步或多设备同步时，必须设计冲突解决、身份边界和加密策略；不要把 SQLite 当作共享服务端数据库。

## Design 必填问题

- 为什么选择 SQLite，而不是 PostgreSQL、MySQL 或纯文件？
- 数据库文件放在哪里？如何设置权限、备份、迁移和清理？
- 是否有多进程、多线程或多实例访问？写入者数量是多少？
- 是否启用 WAL、foreign keys、STRICT tables、busy timeout？
- 数据损坏、磁盘满、用户删除文件、版本降级如何处理？
- 是否需要同步到服务端或跨设备同步？冲突如何解决？

## Spec Review 检查项

- SQLite 的嵌入式定位清楚，没有承担高并发服务端职责。
- 外键、事务、WAL、文件路径和备份策略明确。
- 迁移有版本表、失败恢复和测试计划。
- 关键查询有索引和 `EXPLAIN QUERY PLAN` 验证计划。
- 多进程访问、文件损坏和同步冲突有处理策略。
