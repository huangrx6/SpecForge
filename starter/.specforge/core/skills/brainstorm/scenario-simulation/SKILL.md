# 场景模拟

本 skill 用来检验方案在真实场景里会怎样，而不是重复描述方案好处。它特别适合 `deep` profile；`light` 和 `research-heavy` 只有在场景会改变推荐时使用。

## 前置输入

- `发散方向池` 中进入收敛的候选方案。
- `问题重构` 中的目标用户、约束、非目标和成功标准。
- `当前事实与研究证据` 中的 confirmed / likely / unclear 事实。
- 已知的 UI、技术、依赖、权限、安全或验收约束。

## 场景类型

| 场景 | 要回答的问题 |
|---|---|
| 模糊输入 | 用户只有模糊目标时，系统先问什么？ |
| 现有方案优化 | 什么必须保留？什么可以大胆改？ |
| 重复使用 | 高频用户第 20 次使用时是否仍高效？ |
| 新手进入 | 没有背景的新用户能不能理解下一步？ |
| 失败路径 | 假设、依赖、数据或用户行为错误时会怎样？ |
| 权限 / 安全 | 谁能看到、修改、导出、审批或回滚？ |
| 运营维护 | 后续谁维护？哪里会变贵？ |
| 下游交接 | 进入 PRD / requirements / UI / tech design 前必须满足什么？ |

## 场景优先级

当 profile 只允许模拟少量场景时，按下面顺序选择；不能因为容易写而跳过更可能推翻推荐的场景。

| 优先级 | 场景 | 触发条件 | 理由 |
|---|---|---|---|
| 必须（任何 profile） | 失败路径 | 有候选方案进入推荐或比较 | 失败路径最容易推翻推荐，必须优先压测 |
| 必须（有 UI 时） | 首次使用 / 新手进入 | 方案涉及页面、交互、信息架构、引导或空状态 | 方向确认前必须验证新用户能否理解下一步 |
| 必须（有依赖决策时） | 技术依赖失败 | 方案涉及新增依赖、版本升级、AI provider、外部服务或运行时约束 | 依赖失败会改变 tech-design 交接和回退策略 |
| 按需 | 权限 / 安全 | 多角色、敏感数据、导出、审批、回滚或隐私边界存在时 | 权限错误可能改变范围和验收标准 |
| 按需 | 运营维护 | 长期成本、内容维护、模型 / 依赖费用或人工流程敏感时 | 维护成本会改变 MVP 和后续阶段安排 |
| 低优先 | 重复使用 | deep profile 或高频工作流明确存在时 | 通常用于打磨效率，不应挤掉失败路径或首次使用 |

## Profile 用法

| Profile | 场景数量 | 必须覆盖 |
|---|---:|---|
| `light` | 0-2 | 优先失败路径；有 UI 时加首次使用；否则写 N/A 理由 |
| `deep` | 3-5 | 失败路径、首次使用或依赖失败、边界条件、下游交接 |
| `research-heavy` | 1-3 | 事实不确定时的影响、依赖失败、补证路径、升级 research 条件 |

## 执行步骤

1. 先按“场景优先级”选择关键场景；`deep` profile 至少包含一个失败场景。
2. 写清场景里的用户状态、触发输入、系统响应和下一步。
3. 标出风险：理解失败、流程中断、权限漏洞、成本膨胀、依赖不稳、验证困难。
4. 判断风险是否改变推荐。如果会改变，把它写回 `问题地图` 或 `批判质疑`。
5. 对需要事实的风险，交给 `research-source`；对需要实验的风险，交给 `sf-discovery` research。

## 场景选择矩阵

| 候选类型 | 优先模拟 |
|---|---|
| UI / 体验方向 | 首次使用、高频重复、错误输入、空状态 |
| 技术路线 | 依赖失败、版本冲突、性能边界、回滚 |
| Agent skill | 模糊输入、信息不足、用户反驳、下游交接 |
| 流程 / 审批 | 权限变化、多人协作、撤回、超时 |
| 研究型决策 | 来源冲突、证据不足、需要账号、需要实测 |

## 输出格式

```md
## 场景模拟

| 方案 | 场景 | 用户输入 / 状态 | 系统表现 | 风险 | 需要调整 | 影响推荐 |
|---|---|---|---|---|---|---|
| | | | | | | yes / no |
```

## 质量门槛

- 不只写理想路径，必须包含失败或边界路径。
- 场景要具体到用户动作和系统响应。
- 如果模拟暴露新的高影响决策，必须加入 `[必须确认]`。
- 如果场景不影响推荐，允许写 `N/A + 理由`，不要为了填表编故事。
- 每个风险都要有处理方向：调整方案、补事实、问用户或交给下游。

## 常见失败

| 失败 | 表现 | 修正 |
|---|---|---|
| 只写收益 | “用户体验更好” | 写具体输入、响应和风险 |
| 场景太泛 | “用户使用系统” | 写用户状态、触发点、下一步 |
| 忽略失败 | 只模拟成功路径 | 增加依赖失败、权限错误、误操作 |
| 不回写结论 | 发现风险但不影响矩阵 | 写入 `批判质疑` 或 `问题地图` |

## 交接

- 把改变推荐的风险交给 `critic-review`。
- 把仍可行但需要排序的方案交给 `decision-matrix`。
- 把验证路径交给 `execution-planning` 或后续 verification。

## 自检清单

- 是否至少模拟了一个失败或边界场景？
- 是否写清用户输入 / 状态，而不是只写抽象收益？
- 是否标明哪些风险会改变推荐？
- 是否把事实缺口交给 `research-source`？
- 是否把下游必须处理的场景写入交接？
