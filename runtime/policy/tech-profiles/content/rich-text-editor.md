# Rich Text Editor

## 定位

富文本编辑器适合面向非技术作者、需要所见即所得、块级内容或复杂排版的后台。它的成本明显高于 Markdown，因此不能作为默认选择。

选择富文本时，design 必须明确编辑器数据模型、存储格式、渲染策略、安全边界、迁移方案和测试成本。

## 适合

- 运营、编辑、客户等非技术作者频繁写内容。
- 需要粗体、链接、图片、表格、引用、嵌入内容等可视化编辑。
- 内容有明确的后台审核、发布、撤回流程。
- 需要在编辑端尽量接近公开页视觉。

## 不适合

- 小型 MVP、低频内容配置或作者接受 Markdown 的场景。
- 内容以代码、文档、技术文章为主，Markdown 更可控。
- 没有时间处理 sanitizer、序列化、编辑器边界和迁移风险。
- 第一版只需要完成文章 CRUD。

## 默认能力

| 能力 | 默认 | 说明 |
| --- | --- | --- |
| 编辑器模型 | 必须选定 | HTML、JSON document、Markdown bridge 不能混写 |
| 存储格式 | 推荐结构化 JSON 或受控 HTML | 取决于编辑器生态和渲染端 |
| 渲染 | 独立 renderer | 不直接信任编辑器输出 |
| 上传 | 按项目需要 | 涉及鉴权、病毒/类型检查、对象存储和清理 |
| 扩展 | 白名单 | 禁止任意 HTML 和脚本能力 |
| 迁移 | 必填 | 编辑器替换成本高，需预留数据迁移策略 |

## 技术选择维度

| 方案 | 适用倾向 | 风险 |
| --- | --- | --- |
| TipTap / ProseMirror 类 | 块级扩展、现代编辑体验 | 学习成本和 schema 设计成本较高 |
| Slate 类 | 强自定义编辑体验 | 维护成本高，边界 bug 需要经验 |
| Quill 类 | 常规富文本 | 数据模型和定制能力需提前评估 |
| 受控 HTML editor | 简单排版 | XSS、样式漂移和迁移风险较高 |

Spec 阶段只允许列候选，不允许把“富文本编辑器”当作一个已经解决的问题。

## 设计必填问题

- 作者是否真的需要所见即所得？Markdown preview 能否满足？
- 需要哪些块或 inline marks：标题、列表、引用、代码、图片、表格、嵌入、分割线？
- 数据格式是什么：HTML、JSON、Markdown，如何迁移和导出？
- 前台渲染是否使用同一套 schema？如何保证样式一致？
- 粘贴 Word/网页内容时如何清理格式？
- 图片上传、删除、替换和孤儿资源如何处理？
- 是否需要撤销重做、自动保存、版本历史、审核流？
- 移动端编辑体验是否是需求范围？

## 实现约束

- 编辑器 schema、renderer、serializer、deserializer 要集中管理。
- 保存前要校验内容结构，不要只相信前端编辑器状态。
- 渲染 HTML 必须经过 sanitizer 或安全 renderer。
- 第三方编辑器扩展要记录许可证、包体积、维护活跃度和 SSR/CSR 兼容性。
- 粘贴、上传、撤销、空文档、超长文档必须有测试或手动验证记录。
- 编辑器输出不能直接绕过权限、审核和发布状态。

## 推荐组合

- `frontend/next-app-router-tailwind-ts` + `backend/next-api-routes`：内容后台和公开展示同仓库时使用。
- `database/rdbms-postgresql` / `database/rdbms-mysql`：存储 document、版本、发布状态和审计字段。
- `security/owasp-top10-defenses`：任何富文本公网展示都必须启用。
- `testing/vitest-playwright`：P0 覆盖编辑、粘贴、上传、保存、发布和公开页。

## 验证

- 单元测试覆盖 schema 校验、序列化、反序列化、安全渲染。
- E2E 覆盖常见格式编辑、粘贴清理、上传失败、保存恢复、公开展示。
- 安全测试覆盖脚本注入、危险链接、事件属性、iframe/embed 白名单。
- 如果支持版本历史，覆盖回滚后公开页和编辑器重新打开。

## Spec Review 检查项

- 是否证明 Markdown preview 不够用？
- 是否明确编辑器库、数据模型、renderer 和 sanitizer？
- 是否说明上传、粘贴、移动端和迁移策略？
- 是否把富文本带来的测试范围写入 tasks？
