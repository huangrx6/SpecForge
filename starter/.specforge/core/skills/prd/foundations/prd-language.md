# 产品需求文档语言

产品需求文档写产品决策语言，不写工程规格语言。它解释为什么做、做什么、给谁做、第一版做什么、如何判断成功，而不是怎么实现。

## 推荐写法

| 内容 | 写法 |
|---|---|
| 问题 | `目标用户在 <场景> 中无法 <完成目标>，导致 <代价>` |
| 目标结果 | `本版本希望让 <用户> 能够 <结果>，用 <指标> 观察` |
| 最小可行版本 | `最小可行版本包含 <能力>，因为它直接支撑 <用户价值 / 业务目标>` |
| 非目标 | `本期不做 <能力>，避免 <风险 / 范围膨胀>；后续触发条件是 <条件>` |
| 成功标准 | `用 <可观察指标> 判断是否改善 <问题>` |
| 下游交接 | `需求阶段需要把 <种子> 转成可测试行为` |

## 禁止写法

- “系统必须使用 Redis / Vue / GraphQL / 某 SDK”。
- “按钮使用红色 badge / shadcn Table / 三列布局”。
- “REQ-001 / AC-001” 这类需求和验收编号。
- “执行 npm test / playwright 命令”。
- “智能、完善、高效、易用”但没有指标或观察证据。
- “按最佳实践实现”。

## 验收种子与验收标准

产品需求文档可以写验收种子，但不能写最终验收标准。

```md
验收种子:
- 客户经理打开提醒页面时，应能看到即将到期客户、到期时间、剩余天数和联系状态。
```

交给需求阶段后，才转成场景化验收步骤和需求 / 验收编号。
