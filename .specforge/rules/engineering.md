# 工程规则

工程规则用于约束实现阶段。它不替代语言、框架或团队自己的编码规范，而是给 AI Agent 一个跨项目的最低工程纪律。

## 基本原则

- 改动必须限定在 active change 的范围内。
- 优先沿用当前项目模式、目录结构、命名、错误处理和测试方式。
- 不为了“看起来更优雅”引入新抽象。抽象必须服务当前重复、复杂度或边界问题。
- 行为变更、结构重构、依赖升级、格式化清理应尽量拆开。
- 如果代码变更影响长期项目事实，必须更新 `.specforge/project/`。
- 给审查者留下足够证据，说明改了什么、为什么改、怎么验证。

## 变更大小

优先小而完整的变更：

- 一个 change 解决一个主要问题。
- diff 应能被 reviewer 在合理时间内理解。
- 重构应尽量先行或后置，避免和功能行为混在一起。
- 大 change 必须在 design 中写清拆分失败的原因和 review 策略。

实现中发现任务过大时，应暂停并更新 `tasks.md`，不要继续堆叠修改。

## 代码改动要求

- 读取现有代码后再改，优先复用本仓库已有 helper、模式和测试工具。
- 新代码必须有明确 owner 和调用方。
- 公共函数、组件、服务、配置项必须有实际使用场景。
- 错误处理应返回调用方可理解的信息，内部细节写日志，不泄露敏感信息。
- 并发、重试、超时、取消、幂等、事务和资源释放在相关场景必须显式考虑。
- 删除代码前确认没有入口、配置、文档或测试依赖。

## 依赖和工具

- 新增依赖必须说明用途、替代方案和维护风险。
- 不为少量逻辑引入重量级依赖。
- 依赖升级应记录兼容性影响和验证范围。
- 生成代码或自动格式化造成大 diff 时，应单独说明。
- 版本敏感命令和配置必须查官方文档。

## 配置和环境

- 环境差异通过配置表达，不把生产、测试、开发值硬编码到代码。
- 机密配置不得写入仓库；生产密钥应走环境变量、密钥管理系统或部署平台注入。
- Docker Compose、Kubernetes、CI 等运行配置变更必须说明影响环境。
- 配置项应有默认值策略、校验和失败提示。

## 数据和迁移

涉及持久化数据时，design 必须写清：

- schema 变化。
- 数据迁移和回滚。
- 兼容旧数据或旧客户端的策略。
- 数据权限、脱敏、保留和删除规则。
- 验证查询或回归样例。

没有回滚路径的数据变更必须在风险中明确标注。

## 错误、日志和可观测性

- 用户或调用方看到的是稳定错误，不是堆栈、内部类名或密钥片段。
- 日志应帮助定位问题，至少包含事件、对象标识、结果和相关 trace/correlation id。
- 不记录明文密钥、token、密码、身份证件、完整手机号等敏感数据。
- 新增关键链路应考虑指标、日志或追踪，便于 verification 和上线后观察。

## 完成证据

实现报告至少包含：

- 改动摘要。
- 关键文件。
- 行为变化。
- 验证命令和结果。
- 未覆盖风险。
- 是否需要更新 SSoT。

- Conventional Commits 为提交历史提供机器可读的变更语义：https://www.conventionalcommits.org/en/about/
