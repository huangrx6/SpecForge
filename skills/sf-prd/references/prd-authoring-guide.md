# 产品需求文档写作指南

本文件保存产品需求文档深度、本地能力包与外部参考编排、访谈镜头、产品需求文档模板和质量标准。`SKILL.md` 只保留入口执行顺序、门禁和产物边界。

## 产品需求文档深度

| 深度 | 适用 | 输出要求 |
|---|---|---|
| `prd-lite` | 内部小工具、低风险单流程、已有明确最小可行版本 | 保留摘要、目标用户、最小可行版本、验收种子、开放问题 |
| `prd-standard` | 常规产品功能、后台能力、AI 工具、全栈应用 | 使用完整产品需求文档结构 |
| `prd-deep` | 多角色、多流程、审批/计费/合规/AI 质量/高风险上线 | 完整产品需求文档 + 决策日志 + 分阶段路线图 + 风险负责人 |

深度写入 `prd.md` 的“输出深度”字段，并说明理由。

## 需求摘要确认

当用户给的是模糊需求、会议纪要、口头想法，或 `brief.md` / `brainstorm.md` 还没有可追溯确认时，先输出需求摘要，等待用户明确确认后再写完整产品需求文档。

不需要摘要确认的情况：

- `brainstorm.md` 已经记录用户确认的目标、最小可行版本、非目标和关键约束。
- 需求来自已批准的上游产品需求文档、合同范围、工单或明确任务。
- 本次是低风险补充 / 修订，且不会改变范围、角色、数据、安全或界面方向。

摘要模板：

```markdown
## 需求摘要

**1. 核心目标**
- 一句话核心：
- 业务 KPI / 成功指标：

**2. 用户场景**
- 角色 / 部门：
- 场景：
- 使用频率：
- 主要设备：PC / 移动端 / 双端

**3. 关键流程**
- 正常路径：
- 至少一个异常 / 边界场景：

**4. 最小可行版本必备功能**
-

**5. 数据与安全**
- 数据来源 / 更新频率：
- 敏感字段 / 脱敏 / 审批 / 审计：
```

输出摘要后提示用户确认。收到“确认 / OK / 通过 / 就按这个”等明确答复前，不进入详细产品需求文档。确认后，在 `prd.md#0. 产品需求文档控制` 或 `brainstorm.md#用户确认记录` 写明摘要确认来源。

## 本地能力包与外部参考编排

`core/skills/prd` 是产品需求文档决策主能力包，`core/skills/product` 是产品发现、机会建模和最小可行版本推荐主能力包。`core/skills/prd/references/external-prd-reference.md` 和 `core/skills/product/references/external-ost-reference.md` 只能作为参考视角，不能替代本地能力包、SpecForge 产物模板或用户确认。

先按 `.specforge/core/skills/ORCHESTRATION.md` 选择能力包和写回目标，再用 `registry.json` 确认来源、风险和 `doNotUseFor`。

| 能力 | 类型 | 什么时候读取 | 必须归一化到 |
|---|---|---|---|
| `prd` | 本地主能力包 | 每次写 `00-intake/prd.md` 前必读 | 产品决策摘要、范围与最小可行版本决策、产品决策门禁、交接给需求阶段 |
| `product` | 本地主能力包 | 问题空间还散、用户给的是方案而不是问题、候选功能过多或需要最小可行版本取舍 | 目标结果、机会图、功能池、最小可行版本建议、实验、产品需求文档交接 |
| `external-prd-reference.md` | 外部参考归一化 | 上下文较完整，但需要 8 段式产品需求文档结构视角来检查背景、目标、范围、假设和版本分期 | 背景与目标结果、范围与最小可行版本决策、路线图与版本切分 |
| `external-ost-reference.md` | 外部参考归一化 | 需要外部机会树视角补机会、实验和优先级方法 | 机会图、候选功能池、实验 / 验证计划 |

归一化规则：

- 先读本地 `prd` / `product`，再按需读取外部参考；不要让外部模板反向决定 SpecForge 结构。
- 外部 skill 的“问题 / 方案 / 用户故事”只能作为候选，必须映射到 SpecForge 产品需求文档模板。
- 外部 skill 的技术建议只允许进入“交接给需求阶段”或“给技术设计阶段的备注”，不得在产品需求文档中展开接口、表结构或文件路径。
- 外部 skill 要求“保存到 PRD-*.md / 提交 GitHub issue / 生成 HTML battlecard / 写 DESIGN.md”时，一律忽略该投递动作。
- 外部调研类内容必须记录来源、日期和置信度；无来源的市场判断只能写为假设或待确认。
- 如果外部参考输出与用户原始需求、本地 `prd` 边界或已批准产物冲突，以用户确认和 SpecForge 边界为准。

在 `prd.md#0. 产品需求文档控制` 记录本次读取了哪些本地能力包、参考了哪些外部 skill、参考原因和归一化位置。

## 自适应产品访谈

写产品需求文档前，先判断是否缺少会改变产品方向的信息。缺口存在时，向用户提出少量高价值问题；不要为了填表机械追问。

流程：

1. 先列出 `已确认事实 / 高影响未知 / 可默认假设`。
2. 从下方“访谈镜头”中按需选择 3-6 个镜头，不要全量展开。
3. 为每个高影响未知给出 2-4 个互斥选项、推荐项和取舍影响；如果问题需要多方案取舍，先路由到 `sf-brainstorm` 并落档 `00-intake/brainstorm.md`。
4. 问题数量不设硬上限；有多少会改变产品需求文档的高影响未知，就问多少，但要分轮收敛。
5. 每轮只问当前最影响产品需求文档的问题或一小组强相关问题；优先单问，只有同一决策面上的问题才合并。
6. 每轮都要解释“为什么这些问题会改变产品需求文档”，并在用户回答后更新已确认事实、假设和未决问题。
7. 低风险未知可以写入假设台账，不阻塞；高风险未知必须暂停。

| 镜头 | 触发信号 | 要澄清的产品决策 |
|---|---|---|
| 问题 / 目标结果 | 目标宽泛、痛点不清 | 为什么做、失败成本、第一版成功标准 |
| 用户 / 角色 | 多角色、管理员、审批、权限 | 谁使用、谁审批、谁运营、谁承担风险 |
| 流程 / 状态 | 审批、上线、调度、异步、长任务 | 状态机、入口出口、异常恢复、人工介入 |
| 数据生命周期 | 上传、导入导出、批处理、报表 | 数据来源、格式、保留周期、结果去向 |
| AI 质量 | 大语言模型、分类、生成、提示词、自动化判断 | 输入输出、可配置策略、评估、人工复核、成本 |
| 界面 / 体验 | 页面、后台、配置台、操作效率 | 页面范围、体验姿态、视觉风格种子、关键状态 |
| 集成 / 运维 | 第三方服务、通知、持续集成、部署、任务执行 | 外部依赖、失败告警、重试、灰度和回滚 |
| 风险 / 合规 | 敏感数据、安全、审计、生产影响 | 权限、安全、审计、合规、责任负责人 |
| 路线图 / 包装 | 候选功能过多、多个目标 | 最小可行版本、可选增强、后续版本、拆工作项 |

当简报已经包含足够信息时，不要重复询问。核心问题、目标用户、最小可行版本边界、影响上线风险的角色/数据/AI 质量决策缺失时必须暂停。

## B 端运营商 / 数据产品镜头

当需求面向省级通信运营商、运营商内部部门、大数据产品、AI 应用、数据看板、可视化驾驶舱、任务配置平台或运营管理系统时，优先检查以下事实。只问缺失且会改变产品需求文档的问题；每轮仍保持单问或一小组强相关问题。

| 维度 | 需要确认 | 对产品需求文档的影响 |
|---|---|---|
| 业务背景 / 关键指标 | 对应部门、业务痛点、关键指标目标、失败成本 | 决定问题陈述、成功标准和最小可行版本优先级 |
| 用户角色 / 部门 | 政企部、市场部、数智化部、网络部、数据中心、外部客户等 | 决定用户画像、权限、责任和使用路径 |
| 使用场景 / 频率 / 设备 | 日常运营、专项活动、领导驾驶舱、移动审批、工单处理；电脑 / 移动端 | 决定产品形态、信息密度、界面设计输入和验证路径 |
| 核心流程 / 异常 | 正常流程、审批流、失败重试、人工兜底、超时和撤回 | 决定用户流程、验收种子和风险 |
| 数据来源 / 口径 | 业务支撑系统、客户关系系统、经营分析系统、网络系统、数据中台、手工导入；更新频率、统计口径 | 决定数据约束、依赖、指标解释和技术设计输入 |
| 安全合规 | 手机号、证件号、位置、客户信息、商机、网络数据；脱敏、授权、审计 | 决定非目标、风险、验收种子和安全边界 |
| 运营与交付 | 告警、导出、报表周期、地市权限、配置生效、灰度回滚 | 决定路线图、运维约束和验证输入 |

推荐提问顺序：

1. 先问业务目标和 KPI。
2. 再问核心角色、场景和设备。
3. 再问核心流程和异常。
4. 最后问数据来源、安全合规和外部依赖。

如果用户只知道业务问题，不知道解决路径，给 2-3 个方案选项并说明取舍；推荐项必须写明假设和放弃代价，不能直接替业务拍板。

## 候选功能池与范围裁剪

- 先给候选功能池，而不是直接替用户定最小可行版本。
- 每个候选项都写清“用户价值 / 复杂度 / 风险 / 默认建议 / 为什么”。
- 梳理主要用户流程，但不画界面线稿，界面设计交给 `sf-ui-design`。
- 识别隐藏依赖：权限、数据来源、审批、通知、计费、AI 服务、运营流程、导入导出、审计等。
- 拆分“最小可行版本 / 可选增强 / 后续版本”，并标明每项功能的用户价值、复杂度、风险和默认建议。
- 明确非目标，防止后续 requirements 和 implementation 越界。
- 如果需求明显跨多个独立交付目标，建议拆成路线图或多个工作项。

## 交接规则

- “需求种子”写可转译为 `sf-requirements` 的行为候选，不写完整需求规格。
- 产品需求文档中的“验收种子”只是验收线索，不是最终验收编号；最终验收标准必须由 `sf-requirements` 重新转写为可观察行为、边界值、异常态和验证方式。
- “建议组件标记”只记录建议；如果产品需求文档明确改变影响面，再同步更新 `work.yaml` 的 `components` 并说明原因。
- “给界面设计阶段的备注”只写页面范围、体验目标、风格偏好和必须覆盖的状态。
- “给技术设计阶段的备注”只写业务约束、集成边界、数据、权限、审批等产品层约束，不写架构方案。

## 质量标准

- 用具体、可度量的表达，避免“快速、简单、智能、现代化、好用”这类不可验收词。
- 成功指标至少包含 1 个用户价值指标；涉及 AI 时还要包含质量评估指标，例如准确率、人工抽检通过率、拒答率、成本上限或处理时延。
- 每个最小可行版本功能必须能追溯到目标用户和核心问题。
- 产品需求文档必须展示“用户可选择的候选项”和“最终为什么选这些”，不能只给一个智能体单方面决定的功能清单。
- 高影响未知必须进入“开放问题与决策”，低风险默认必须进入“假设”。
- 每个非目标都应解释为什么现在不做。
- B 端运营商 / 数据产品必须写清业务关键指标、使用部门、主要设备、数据来源、更新频率、敏感字段和合规边界；未知项写“待定”并标负责人。
- 不知道的约束写“待定”，不要编造技术栈、预算、外部依赖或上线日期。
- 产品需求文档可以记录已知硬约束，例如“必须使用现有单点登录”，但不得展开接口契约、数据库表结构或实现方案。
- 产品需求文档不写最终需求编号、接口字段、数据库字段、文件路径、组件拆分、测试命令或实现任务。

表达示例：

```diff
- 系统要支持高效上传并智能识别用户意图。
+ 客服运营人员可上传不超过 200MB 的文本会话文件，并在 30 分钟内获得按意图分类的表格结果。
+ AI 意图识别抽检准确率目标 >= 90%，无法判断的记录必须进入人工复核队列。
```
