# Markdown Textarea

## 定位

最轻量的内容编辑方案。适合 MVP、内部工具、低频写作、配置型内容和用户愿意直接写 Markdown 的场景。

它不是“内容后台的默认答案”，而是“先把内容结构跑通”的低复杂度选择。只要需求出现实时预览、图片管理、目录、代码高亮、写作快捷键或多人使用，就要升级到 `content/markdown-preview-editor`。

## 适合

- 管理员或开发者自己写内容。
- 表单里只有少量 Markdown 字段，例如公告、简介、FAQ。
- 项目优先验证信息架构、发布流程和展示页面。
- 可接受没有所见即所得体验。

## 不适合

- 面向非技术作者的内容后台。
- 文章较长，作者需要实时预览排版。
- 需要图片拖拽上传、资源库、目录、脚注、代码高亮预览。
- 需要复杂协作、评论、版本历史或块级编辑。

## 默认能力

| 能力 | 默认 | 说明 |
| --- | --- | --- |
| 输入组件 | 原生 `textarea` | 保持低依赖和可维护性 |
| 存储格式 | 原始 Markdown | 数据层不保存 HTML 作为唯一来源 |
| 渲染 | 展示端统一渲染 | 编辑端可不提供实时渲染 |
| 消毒 | 必须显式决策 | 多用户或公网内容必须有 sanitizer |
| 图片 | 不内置 | 可用 URL 输入或延后到 preview editor |
| 自动保存 | 默认不做 | 需要时必须写入交互设计 |

## 设计必填问题

- 作者是谁：开发者、站长、运营、普通用户？
- Markdown 支持到什么范围：标题、列表、链接、图片、表格、代码块、HTML？
- 是否允许原始 HTML？如果允许，谁负责消毒和白名单？
- 用户离开页面时，未保存内容如何提示？
- 是否需要草稿、发布、撤回、预览链接？
- 是否需要从 textarea 升级到预览编辑器的兼容路径？

## 实现约束

- 表单状态要区分 `dirty`、`saving`、`saved`、`failed`。
- 保存失败时不能清空输入内容。
- 展示端 Markdown 渲染逻辑必须集中封装，不要在多个页面散落不同 renderer。
- 渲染 HTML 时默认禁用危险 HTML；如果开启 HTML，必须在 design 里记录 sanitizer、白名单和测试证据。
- 长文本字段需要设置合理的最小高度、可调整高度或全屏编辑入口。

## 推荐组合

- `frontend/react-vite-tailwind-ts`：静态展示站、作品集、轻量后台。
- `frontend/vue-vite-tailwind-ts`：Vue 团队的轻量内容配置。
- `testing/vitest-playwright`：覆盖保存、重新打开和展示端渲染。

## 验证

- 单元测试覆盖标题、列表、链接、代码块、危险 HTML。
- E2E 覆盖创建、编辑、保存失败、重新打开、公开页面渲染。
- 公网内容必须验证 XSS payload 不会作为可执行脚本进入页面。

## Spec Review 检查项

- 是否说明选择 textarea 而不是预览编辑器的理由？
- 是否定义 Markdown 子集和 HTML 安全策略？
- 是否覆盖未保存、保存失败和重新打开状态？
- 是否说明未来升级到 richer editor 时的数据兼容性？
