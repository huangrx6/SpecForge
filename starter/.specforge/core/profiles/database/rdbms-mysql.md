# MySQL Relational Database

## 适用 / 不适用

适用：

- 团队已有 MySQL 运维、监控、备份、迁移和调优经验。
- 传统 Web、Java、PHP、Rails、Go、Node 服务需要稳定关系型存储。
- 数据模型以清晰的 OLTP 读写、事务、唯一约束和普通索引为主。
- 生态或平台强绑定 MySQL，例如现有 RDS、Aurora MySQL、PlanetScale、TiDB 兼容层或企业标准。

不适用：

- 需要 PostgreSQL 特有扩展能力，例如 PostGIS、丰富表达式/部分索引策略或复杂 JSONB 查询。
- 单机嵌入式、本地文件型、测试 fixture 优先的场景，优先看 `database/embedded-sqlite`。
- 多区域强一致、复杂分析查询或搜索系统，不应只靠单个 MySQL OLTP 实例解决。

## 默认组合

| 能力 | 默认建议 | 说明 |
|---|---|---|
| 存储引擎 | InnoDB | 事务、行级锁和外键能力以 InnoDB 为基线 |
| 字符集 | `utf8mb4` | 避免 emoji、多语言字符被截断或报错 |
| 排序规则 | 项目统一指定 | 大小写、重音、唯一约束行为会受 collation 影响 |
| 主键 | BIGINT 自增或业务确认的 UUID/ULID | UUID 随机写入会影响聚簇索引局部性，需要评估 |
| 金额 | `DECIMAL` | 禁止 `FLOAT` / `DOUBLE` 保存金额 |
| 迁移 | Flyway / Liquibase / Prisma / Drizzle / Alembic | 迁移文件进入版本控制 |

## Schema 与约束

- 默认使用 InnoDB，不要混用 MyISAM 等不支持事务和外键的引擎。
- 表、列、索引命名保持项目内统一；新项目默认 `snake_case`。
- 明确 `NOT NULL`、默认值、唯一约束、外键约束和检查逻辑。
- MySQL 外键列必须有索引；即使不建物理外键，也要说明应用层一致性和索引策略。
- `VARCHAR` 长度不要随手写 255；依据业务、索引长度和校验规则决定。
- JSON 字段只用于扩展属性或第三方 payload；高频过滤和核心关系应落成普通列。

## 索引与查询

- 复合索引按查询形态设计，遵守最左前缀原则。
- 高频 `WHERE`、`JOIN`、`ORDER BY`、唯一约束和外键列要有索引计划。
- 低基数字段单列索引要谨慎，通常需要结合其他字段形成复合索引。
- 分页策略要避免深分页退化；大数据量列表考虑 keyset pagination。
- 全文搜索只适合边界清楚的文本检索；复杂搜索、分词和相关性排序应评估搜索引擎。

## 事务、迁移与运行

- 事务中只放必须原子提交的数据库操作，外部 HTTP、邮件、消息投递放到事务外或 outbox。
- DDL 发布采用后向兼容步骤：加字段、双写或回填、切读、加约束、清理旧字段。
- 大表改列、加索引、回填要评估锁和复制延迟；必要时使用在线迁移工具或托管平台能力。
- 连接池、最大连接数、慢查询日志、复制延迟、备份恢复和容量增长要写入运行设计。
- MySQL JSON、全文索引、生成列等能力使用前必须说明查询方式和测试证据。

## Design 必填问题

- 为什么选择 MySQL，而不是 PostgreSQL、SQLite 或非关系型存储？
- 字符集和 collation 是什么？唯一约束是否受大小写敏感性影响？
- 核心表、主键、外键、唯一约束和删除策略是什么？
- 高频查询和分页路径是什么？复合索引如何排序？
- 是否需要在线迁移、数据回填、复制延迟评估或连接池调参？
- 备份恢复、审计、PII 和数据保留策略是什么？

## Spec Review 检查项

- 选择 MySQL 的生态、团队或平台理由清楚。
- 明确 InnoDB、`utf8mb4`、collation 和迁移工具。
- 金额不用浮点数，时间和时区策略清楚。
- JSON 没有替代核心关系模型。
- 高频查询、唯一约束和外键列有索引策略。
- 大表 DDL、连接池、备份恢复和慢查询观测有计划。
