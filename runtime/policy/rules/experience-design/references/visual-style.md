# Visual Style Guide

UI design 阶段必须先确认视觉风格，再产出线稿或原型。风格确认不是让用户选颜色，而是把产品气质、信息密度、组件形态和实现约束收敛成可执行的 `style brief`。

## 什么时候必须问用户

以下任一情况成立时，必须向用户确认风格方向：

- 项目没有现成设计系统、品牌手册、Figma 文件或组件库规范。
- 本次 work item 新增主要页面、后台、仪表盘、编辑器、审批台、配置台或对外页面。
- 用户提到“好看”“风格”“主题”“配色”“像某某产品”“参考某个网站”。
- UI 会影响产品识别度、用户信任、商业展示或团队长期复用。

以下情况可以不追问，但要写明默认假设：

- 本次只修改已有页面中的一个小控件，并明确沿用现有设计系统。
- 纯后端 / 纯配置 / 纯任务调度，无用户可见界面。
- 紧急 bugfix 只恢复既有 UI 行为，不引入新视觉决策。

## 风格澄清方式

不要把问题问成“你喜欢什么颜色”。应给用户少量可选方向，并允许用户补充。

推荐话术：

```text
这个需求有 UI 影响。开始原型前我需要确认视觉风格方向。

我建议你从下面选一个，或告诉我参考产品：
1. 企业后台 / 数据密集：紧凑表格、清晰状态、低装饰，适合高频操作。
2. 开发者工具 / 工程化：中性底色、代码感、强信息层级，适合配置和任务执行。
3. 现代 SaaS / 轻量运营：更友好、更留白，适合非技术用户。

确认后我会把它写进 ui-design.md，并据此选择 Pencil / Figma / HTML / ASCII 原型方式。
```

## 可参考的风格来源

getdesign.md 这类 DESIGN.md 风格库可以作为灵感来源：它把真实产品的设计系统分析成风格关键词、Token 和规则，适合用来描述“像哪类产品”，但不能照搬品牌资产。

使用方式：

- 让用户选择参考对象：例如 “Linear-like”、 “Intercom-like”、 “Notion-like”、 “Stripe-like”。
- 转译为项目语言：不要写“复制 Linear”，而写“精确、低噪声、紧凑列表、紫色只作强调”。
- 避免品牌侵权：不复用对方 Logo、专有插图、商标色组合或可识别页面布局。
- 保持领域适配：后台、CRM、客服、审批、数据标注等工具应优先考虑可扫描、可比较、可高频操作。

## Style Brief 模板

在 `ui-design.md` 中记录：

```markdown
## Visual Style Brief

| 项 | 结论 |
|---|---|
| 用户确认 | 2026-05-14，用户选择“企业后台 / 数据密集” |
| 参考方向 | Intercom 的客服语境 + Linear 的低噪声列表，不复用品牌元素 |
| 产品气质 | 可信、清晰、高频操作友好 |
| 信息密度 | 紧凑；表格和配置表单优先可扫描 |
| 色彩方向 | 中性背景，主色仅用于主要动作和状态强调 |
| 组件形态 | 8px 内圆角，表单、表格、Tabs、Badge、Dialog 为主 |
| 排版 | 系统字体；数字、任务 ID 可使用等宽字体 |
| 动效 | 只用于状态反馈，不做装饰性动效 |
| 暗色模式 | 本期 N/A / 本期包含 |
| 不采用 | 营销式大 Hero、装饰性渐变、过大卡片、低密度布局 |
```

## 候选方向建议

Agent 可按产品类型提出 2-4 个方向，不要一次列十几个让用户疲劳。

| 方向 | 适合 | 关键词 |
|---|---|---|
| 企业后台 / 数据密集 | 审批、客服、运营、报表、管理台 | 清晰、紧凑、低装饰、状态强 |
| 开发者工具 / 工程化 | 配置、任务、CI、AI 工作流、API 平台 | 中性、代码感、日志友好、可追踪 |
| 现代 SaaS / 轻量运营 | CRM、项目管理、营销运营 | 友好、留白适中、组件化、易上手 |
| 内容 / 编辑器 | 博客、知识库、CMS、文档协作 | 阅读优先、编辑器友好、层级清晰 |
| 消费级 / 品牌化 | C 端、活动页、作品展示 | 更强视觉识别、图片和品牌资产驱动 |

## Gate 要求

Spec Review 不审美，但审查是否足以指导实现：

- 有 UI 影响时，必须有 style brief 或“沿用现有设计系统”的证据。
- 若用户未确认，必须记录默认假设和可逆性。
- 若引用外部风格库或参考产品，必须转译为通用设计原则，不能只写“参考某产品”。
- 视觉风格不得与产品领域冲突；高频工作台不能用营销落地页式构图替代业务界面。
