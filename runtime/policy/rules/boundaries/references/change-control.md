# 边界变更和拆分协议

本参考用于回答：实现时发现事情比预想复杂，接下来该继续、暂停、补 spec，还是拆新 change。

## 四类边界变化

| 情况 | 例子 | 处理方式 |
|---|---|---|
| 边界内澄清 | 原设计漏写一个错误态，但不改变责任范围 | 更新 design / tasks，继续实现 |
| 边界扩大 | 原本只改后端，发现必须改前端交互和权限 | 暂停实现，更新 requirements / design，重新过 review |
| 新 change | 当前 bug 暴露出独立的长期重构或平台能力缺口 | 记录发现，拆新 change |
| 隐藏债务 | 当前需求必须依赖一个已有基础缺陷修复 | 判断是否先开前置 change；否则记录风险并暂停 |

## 变更时必须记录

边界变更至少要留下：

- 触发原因。
- 原边界为何不足。
- 扩大后的新增责任。
- 新增影响面和验证面。
- 是否需要重新 spec review。

## 拆分规则

出现以下情况时，应优先拆成多个 change：

- 同时改变需求行为和大规模重构。
- 同时改变多个 owner 的公共契约。
- 同时包含前端、后端、数据迁移、部署和权限，且无法一次验证。
- 验收标准超过一个独立用户目标。
- 一个 diff 需要多个独立 reviewer 才能判断是否正确。
- review 无法在一次完整阅读中判断正确性。

## 快速判断表

| 问题 | 是 | 否 |
|---|---|---|
| 这些改动是否服务同一个验收目标？ | 可继续 | 考虑拆分 |
| 是否由同一个主要 owner 承担？ | 可继续 | 考虑拆分 |
| 是否共享同一套回滚逻辑？ | 可继续 | 考虑拆分 |
| 是否必须在一次发布中同时生效？ | 可继续 | 可以拆分 |
| review 是否能在一次上下文中可靠完成？ | 可继续 | 应拆分 |

## 典型危险信号

- “既然已经改到这里，不如一起……”
- “这块其实早就该重构了。”
- “顺便把接口规范也统一掉。”
- “这不是本需求，但现在不改以后更麻烦。”

这些话有时是对的，但默认不应直接进入当前 change。

## Review Checklist

- 实现中出现的新增问题，是否被正确分类。
- 是否存在应该拆新 change 却硬塞进当前 change 的情况。
- 是否留下了边界变更记录。
- 是否需要重新 spec review。
