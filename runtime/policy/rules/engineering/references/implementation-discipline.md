# 实现纪律

本参考用于约束代码改动的组织方式、粒度和审查质量。

## 变更大小

优先小而完整的变更：

- 一个 change 解决一个主要问题。
- diff 应能被 reviewer 在合理时间内理解。
- 大 change 必须在 design 中写清拆分失败的原因和 review 策略。
- 实现中发现任务过大，应暂停并更新 `tasks.md`，不要继续堆叠修改。

Google 的工程实践指出，小 change 更容易审查、更不容易引入 bug，也更容易回滚。

## 拆分优先级

通常应拆开的内容：

- 行为变更。
- 结构重构。
- 依赖升级。
- 大面积格式化或机械替换。

小范围局部清理可以伴随当前 change，但前提是：

- 它是当前实现的直接前置。
- 不增加理解负担。
- 不掩盖主改动。

## 代码改动要求

- 读取现有代码后再改。
- 优先复用仓库已有 helper、模式和测试工具。
- 新代码必须有明确 owner 和调用方。
- 公共函数、组件、服务、配置项必须有实际使用场景。
- 删除代码前确认没有入口、配置、文档或测试依赖。

## 抽象纪律

不要因为：

- “未来可能会复用”
- “顺手更优雅”
- “看起来更现代”

就提前引入抽象。

可以引入抽象的常见信号：

- 当前需求已出现明确重复。
- 重复逻辑已经影响测试或维护。
- 边界隔离需要一个稳定接口。
- 已有模式在仓库中长期存在，本次只是顺着它延展。

## Code Review Checklist

- 是否只解决一个主要问题。
- 是否把行为变更和重构混在一起。
- 是否复用了现有模式。
- 是否新增了无调用方抽象。
- 是否删除了仍有依赖的代码。
