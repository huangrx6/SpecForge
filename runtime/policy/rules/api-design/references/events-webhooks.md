# 事件、Webhook 和消息

本参考用于设计事件驱动集成、Webhook 回调和消息队列契约。异步接口不是“换个传输方式的 HTTP”，它天然包含投递语义、顺序语义和失败语义。

## 什么时候选事件 / Webhook

| 需求 | 更适合 |
|---|---|
| 内部系统解耦、异步扩展、可广播 | 事件或消息队列 |
| 第三方系统被动接收通知 | Webhook |
| 调用方需要立即同步结果 | REST / RPC |
| 处理时长较长但需要状态追踪 | 任务资源加事件通知 |

不要为了“显得解耦”把本应同步完成的核心事务切成脆弱事件链。

## 事件契约最小集

每种事件都必须明确：

- `event_name` 或 topic。
- `event_id`。
- `event_version` 或 schema version。
- `occurred_at`。
- `producer` 和 owner。
- `subject` 或聚合根标识。
- `payload` schema。
- 生产时机：事务前、事务后、最终一致性还是补偿事件。
- 消费者预期：通知、投影、触发任务还是审计。

推荐基础 envelope：

```json
{
  "event_id": "evt_123",
  "event_name": "order.paid",
  "event_version": "1.0",
  "occurred_at": "2026-05-13T08:00:00Z",
  "producer": "billing-service",
  "subject": "order_123",
  "trace_id": "trc_456",
  "payload": {}
}
```

## 投递与顺序语义

必须写清消息系统对下面问题的承诺：

| 维度 | 需要说明 |
|---|---|
| 投递 | 至多一次、至少一次、是否存在重复 |
| 顺序 | 全局有序、分区有序、同 subject 有序，还是不保证 |
| 重放 | 是否支持 replay，保留多久，如何触发 |
| 延迟 | 实时、近实时、批处理 |
| 去重 | 使用什么幂等 key，去重窗口多长 |
| 消费失败 | 重试、死信、告警、人工重放 |

如果系统只保证“至少一次”，消费端必须按重复消息设计。

## 幂等与去重

消费者必须能抵御重复投递。

常见方案：

- 用 `event_id` 做去重。
- 用业务幂等键，例如 `order_id + status`。
- 保存消费游标或处理日志。
- 对副作用操作使用幂等写入。
- 明确去重窗口和过期后的行为。

不要假设消息中间件帮你解决所有重复消费问题。

## Webhook 契约

Webhook 必须明确：

- 回调 URL 注册方式。
- 支持的 event type。
- 签名算法和 header 名称。
- 时间戳容忍窗口。
- nonce 或等价防重放机制。
- 发送超时。
- 重试次数、退避策略和最大投递周期。
- 接收方哪些状态码代表成功。
- 失败后的死信、告警和手工重放方式。

推荐定义：

| 返回码 | 发送方处理 |
|---|---|
| `2xx` | 视为成功 |
| `408` / `429` / `5xx` | 可重试 |
| 其他 `4xx` | 默认不重试，除非协议另行约定 |

## 安全要求

Webhook 和外部事件至少要考虑：

- HMAC 或等价签名。
- 时间戳校验。
- 防重放。
- 密钥轮换。
- TLS。
- 请求来源限制。
- 脱敏日志。
- trace id。

## 版本与兼容

通常兼容：

- 新增可选字段。
- 新增 event type，前提是消费者按订阅关系接收。
- 扩展 payload 中的非破坏性字段。

通常破坏兼容：

- 删除字段。
- 改字段含义、单位、类型。
- 改事件触发时机。
- 改 topic / event name。
- 改顺序或投递承诺。

新版本事件必须说明旧消费者如何迁移，是否允许并行双发。

## SpecForge 落点

- `requirements.md`：写清谁订阅、为什么订阅、业务成功标准。
- `technical-design.md`：写 envelope、schema、投递语义、签名、失败补偿。
- `tasks.md`：拆 producer、consumer、schema、重放、监控、测试任务。
- `verification/report.md`：记录重复投递、重试、签名、死信、回放验证。

## Review Checklist

- 是否明确 topic / event name / webhook path。
- 是否有 envelope 和 payload schema。
- 投递、顺序、重试、死信、重放是否定义。
- 消费者是否具备幂等和去重策略。
- Webhook 是否有签名、时间戳和防重放。
- 版本演进和双发策略是否清楚。
- 是否有失败告警和人工恢复路径。
