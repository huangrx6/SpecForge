# PostgreSQL Relational Database

## 适用 / 不适用

适用：

- 需要强事务、一致性约束、复杂查询、报表查询或多表关系的业务系统。
- 需要 JSONB、全文搜索、地理空间、部分索引、表达式索引等扩展能力。
- 需要云托管、备份恢复、只读副本、连接池和成熟运维生态。

不适用：

- 单机嵌入式或本地文件型应用，优先看 `database/embedded-sqlite`。
- 团队和既有系统主要围绕 MySQL 生态建设，且没有 PostgreSQL 特有需求时，优先评估 `database/rdbms-mysql`。
- 需求没有持久化或只是静态配置时，不要为了完整性引入数据库。

## 默认组合

| 能力 | 默认建议 | 说明 |
|---|---|---|
| 存储引擎 | PostgreSQL 原生关系模型 | 核心关系用表和约束表达，不用 JSONB 逃避建模 |
| 主键 | BIGINT identity 或 UUIDv7 | 需要跨系统生成时选 UUID；高写入局部性要评估 |
| 时间 | `timestamptz` + UTC | 前端展示再按用户时区转换 |
| 金额 | `numeric` / `decimal` | 禁止浮点数保存金额和精确计量 |
| 迁移 | Prisma / Drizzle / Flyway / Liquibase / Alembic | 跟随项目语言生态，但必须版本化 |
| 连接 | 应用连接池或 PgBouncer | Serverless 场景必须显式说明连接策略 |

## Schema 与约束

- 表名、字段名、索引名保持项目内统一风格；新项目默认 `snake_case`。
- 每个业务表说明主键、唯一约束、外键约束、可空策略和删除策略。
- 外键用于表达核心一致性；如果因为性能、分库或历史原因不建外键，必须写明应用层一致性方案。
- JSONB 只用于扩展属性、第三方 payload、低频过滤字段；核心业务关系不要塞进 JSONB。
- PII、密钥、token、隐私字段必须说明加密、脱敏、访问控制和保留期限。

## 索引策略

- 高频 `WHERE`、`JOIN`、`ORDER BY`、唯一约束和外键字段要有索引计划。
- 复合索引必须按查询形态排序，不要为了“保险”堆无用索引。
- 软删除表的唯一约束要考虑 `deleted_at IS NULL` 的部分索引。
- 大表新增索引要评估锁、耗时和回滚方式；需要时采用在线迁移策略。
- 报表、搜索和聚合不要长期压在 OLTP 主路径上；评估物化视图、只读副本或搜索引擎。

## 事务、迁移与运行

- 事务只包数据库一致性，不把外部 HTTP、邮件、消息发送等慢操作塞进事务。
- DDL 采用后向兼容分步迁移：新增字段、双写或回填、切读、加约束、清理旧字段。
- 大规模 backfill 要说明批大小、限速、重试、暂停和恢复。
- 备份恢复必须说明 RPO/RTO、恢复演练或最小验证方式。
- 生产查询需要慢查询观测、连接池指标和错误告警。

## Design 必填问题

- 核心实体和关系是什么？是否需要 ER 图或表关系说明？
- 为什么选择 PostgreSQL，而不是 MySQL、SQLite 或非关系型存储？
- 主键、唯一约束、外键、删除策略和时间字段规范是什么？
- 高频查询、排序、分页和报表路径是什么？索引如何支持？
- 迁移是否后向兼容？是否需要 backfill 或在线索引？
- 是否存在 PII、审计、保留期限、备份恢复或合规要求？

## Spec Review 检查项

- 选择 PostgreSQL 的理由和替代数据库取舍清楚。
- 没有用 JSONB 替代清晰的核心关系模型。
- 金额、时间、删除、审计和 PII 策略明确。
- 高频查询、唯一约束和外键有索引策略。
- 迁移脚本可回放，并有回滚或补偿说明。
- Serverless 或高并发部署有连接池策略。
