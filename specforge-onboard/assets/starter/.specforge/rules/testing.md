# 测试规则

测试规则用于让 verification gate 有证据，而不是只写“已自测”。验证深度要匹配变更风险，既不能为小改动制造过度流程，也不能让高风险变更靠口头确认通过。

## 基本原则

- 验证深度要匹配变更风险。
- 记录命令、结果和已知缺口。
- 没有 evidence 时，不标记 verification complete。
- 测试应证明验收标准，而不是只证明代码执行过。
- 自动化优先；无法自动化时，必须留下可复现手工步骤和证据。

## 测试分层

| 层级 | 适用场景 | 关注点 |
|---|---|---|
| 单元测试 | 函数、类、组件、小型业务规则 | 快速反馈、边界条件、错误分支 |
| 集成测试 | 数据库、缓存、消息、外部服务适配 | 契约、事务、配置、序列化 |
| 契约测试 | API、SDK、RPC、事件、Webhook | 入参、出参、错误码、兼容性 |
| 端到端测试 | 关键用户流程、跨系统链路 | 主路径、权限、环境配置 |
| 回归测试 | bugfix、历史故障、迁移 | 复现样例不再失败 |
| 手工验证 | UI、部署、第三方环境、一次性运维 | 截图、日志、命令、观察窗口 |

测试金字塔不是固定比例，而是提醒：底层快速测试应覆盖大部分逻辑，高层测试覆盖关键链路和风险。

## 风险匹配

| 变更类型 | 最低验证 |
|---|---|
| 文档或模板 | 链接、格式、示例命令检查 |
| 小型纯代码调整 | 相关单元测试或等价命令 |
| API / SDK 契约 | 契约测试、示例调用、兼容检查 |
| 数据迁移 | 迁移前后样例、回滚或补偿验证 |
| 权限和认证 | 正向、反向、越权、过期或缺失凭据 |
| 部署和配置 | 目标环境配置检查、启动检查、回滚步骤 |
| bugfix | 复现失败样例、修复后回归、相邻风险检查 |

## 设计测试策略

`design.md` 中应写清：

- 哪些验收标准由自动化测试覆盖。
- 哪些只能手工验证，以及原因。
- 需要 mock、stub、test container 还是真实环境。
- 外部依赖不可用时的替代验证方式。
- 失败时如何定位，是日志、指标、截图还是命令输出。

## verification evidence

`05-verification/report.md` 至少包含：

- 验证范围。
- 执行命令。
- 结果摘要。
- 失败项和处理方式。
- 未覆盖风险。
- 证据路径，例如日志、截图、CI 链接、制品。

`ci-result.md` 应记录：

- CI 名称和链接。
- commit 或构建版本。
- 状态。
- 失败 job 的摘要。
- 是否与当前 change 相关。

## 无法运行测试

如果测试无法运行，不得假装通过。必须记录：

- 为什么无法运行。
- 影响哪些验收标准。
- 使用了什么替代证据。
- 后续由谁在什么环境补验。

只有在风险可接受、替代证据充分时，verification 才能批准。

## 常见反模式

- 只运行格式化或 lint，却声称功能已验证。
- 新增逻辑没有失败用例。
- 只测 happy path，不测权限、空态、错误态。
- 复现 bug 后没有把复现样例沉淀为回归用例。
- 手工验证只写“正常”，没有步骤、环境、截图或日志。
