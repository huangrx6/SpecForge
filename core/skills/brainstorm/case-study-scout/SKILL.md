# 优秀案例侦察

本 skill 负责把“多看看优秀案例”变成可审查的研究动作。它不复制别人的页面、品牌或代码；它只提取可迁移机制：信息架构、交互节奏、视觉完成度、动效目的、工作流组织、反馈方式和取舍逻辑。

## 什么时候使用

- 用户要求“高级一点”“不要老套”“参考优秀网站 / 模板 / 竞品 / 作品集”。
- 需求涉及管理后台、数据看板、工作台、审批流、内容生产、AI 工具、官网、落地页、品牌页、作品集或活动页。
- 方案池只有常见卡片、表格、筛选、弹窗、左右布局，缺少差异化机制。
- UI / 体验方向会影响后续 `sf-ui-design`、Pencil 原型或前端实现成本。
- 竞品、行业案例或优秀作品会影响 MVP 范围、信息架构、交互模式、动效边界或视觉气质。

## 输入

- 用户原始目标、目标用户、业务约束和已有产品事实。
- 现有 `brief.md`、`brainstorm.md`、可选 `prd.md` / `requirements.md` / `ui-design.md`。
- 用户提供的网址、截图、模板站、作品站、竞品或关键词。
- 可用时的浏览器截图、公开页面、官方案例页、作品集、Award / gallery 页面和产品官网。

## 搜索策略

先生成搜索计划，再查询。不要只打开用户给的一个链接就下结论。

| 场景 | 推荐来源 | 目标 |
|---|---|---|
| 管理后台 / 工作台 / SaaS 工具 | 竞品官网、产品 demo、公开 dashboard showcase、组件库案例、行业产品截图 | 任务密度、导航组织、表格/筛选/批量操作、状态反馈、权限和审计机制 |
| 官网 / 品牌页 / 落地页 | Awwwards、Godly、Lapa、Mobbin、品牌官网、同类产品官网 | 首屏叙事、滚动节奏、视觉资产、交互签名、动效目的和转化路径 |
| AI 产品 / Agent 工具 | 官方产品页、docs、changelog、demo video、社区案例 | prompt flow、上下文管理、信任反馈、人机协作边界、结果可编辑性 |
| 内容 / 创作 / 编辑器 | 设计工具、视频/图像/文档编辑产品、CMS、素材管理产品 | 画布组织、资产面板、版本/历史、预览、批处理和导出机制 |
| 移动 / H5 / 活动页 | 品牌活动页、移动端优秀案例、真实小程序/移动 web 截图 | 手势、节奏、微交互、首屏密度、性能风险 |

## 侦察流程

1. **明确侦察问题**：写清本次要找什么，不使用“找一些好看的案例”这种空问题。
2. **设定案例池配额**：默认至少 5 个候选案例；`light` 可 3 个；`deep` / 品牌页 / 高级交互至少 6 个；同质案例超过 2 个要换来源。
3. **多源查询**：组合用户给定网址、同类竞品、优秀作品站、组件/模式库、行业案例。涉及当前事实时，记录访问日期。
4. **看整体体验**：只看截图不够；能访问页面时观察首屏、滚动、状态变化、交互入口、移动端适配和加载感知。
5. **拆机制，不抄外观**：每个案例必须提取可迁移机制和不能照搬点。
6. **反模板化归纳**：指出当前默认方案最可能落入的俗套，并给出 2-3 个能跳出俗套的机制路线。
7. **成本和风险回填**：把动效、3D、视频、AI、实时协作、复杂表格等成本写入方案矩阵，不把“高级感”当免费收益。
8. **交给收敛**：只把机制路线交给 `decision-matrix`、`scenario-simulation` 和用户确认，不直接写成 approved 方案。

## 质量门槛

- 至少覆盖 3 类来源：用户给定案例、同类竞品、优秀作品/模式库；确实无法访问时写 `inaccessible` 和替代来源。
- 每个案例必须写 URL 或明确写用户提供的本地截图路径；不能只写产品名。
- 每个案例必须写“可迁移机制”和“不能照搬”。
- 至少给出 2 条互斥机制路线，而不是把所有好点子堆成一个大方案。
- 视觉、动效或 3D 案例必须写成本和降级策略；不能把炫酷动效默认塞进 MVP。
- 管理后台案例必须说明任务密度、信息架构、批量操作、状态反馈或审计机制中的至少两项。
- 来源只是灵感时标 `likely`；只有实际访问、截图或官方资料支持时才标 `confirmed`。

## 和 research-source 的边界

| 能力 | 使用时机 | 产出 |
|---|---|---|
| `case-study-scout` | 找优秀案例、拆体验机制、避免模板化、形成设计/产品候选路线 | 案例池、机制路线、反模板化提醒 |
| `research-source` | 查版本、价格、法规、API、竞品声明、AI provider 限制等事实 | 证据表、置信度、未查证项、版本关系 |

如果案例声明涉及具体功能、价格、发布状态、性能、安全或法规，交给 `research-source` 查证；不要让案例侦察替代事实查证。

## 禁止

- 不复制竞品文案、品牌资产、专有插画、专有交互或代码。
- 不把 Awwwards / Dribbble 式视觉直接套到管理后台工作流。
- 不用“高级、现代、炫酷”替代机制描述。
- 不把无法访问的页面写成已验证案例。
- 不因案例好看就忽略当前用户任务、性能、可访问性、实现成本和维护成本。

## 自检清单

- 是否真的查了多个案例，而不是只凭记忆举例？
- 是否记录 URL / 截图路径 / 访问日期？
- 是否拆出了机制，而不是只评价审美？
- 是否给出至少两条可取舍机制路线？
- 是否写清哪些东西不能照搬？
- 是否把案例结论交给用户确认，而不是写成已批准方向？
