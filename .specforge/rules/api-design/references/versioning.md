# 版本和演进

API 版本策略的目标不是“多放一个 v1”，而是让调用方能安全迁移，让服务方能持续演进。

## 兼容性分类

通常兼容：

- 新增 endpoint。
- 新增可选请求字段。
- 新增响应字段，前提是调用方应忽略未知字段。
- 扩展错误详情但保持错误码稳定。
- 新增分页元信息。
- 新增非默认能力开关。

可能破坏兼容：

- 新增枚举值，如果调用方没有未知值兜底。
- 改变默认排序。
- 改变字段精度、单位、大小写或格式。
- 改变限流策略。
- 改变错误状态码。

通常破坏兼容：

- 删除或重命名字段。
- 改变字段类型、含义、单位、默认值或 nullability。
- 新增必填请求字段。
- 改变响应包络、分页结构、幂等语义或错误码语义。
- 改变认证机制或权限要求。
- 把同步接口改成异步，或把一次响应改成流式响应。

## 版本策略

| 策略 | 示例 | 适用场景 | 注意事项 |
|---|---|---|---|
| URI major version | `/v1/users` | 公共 REST API | 最直观，但路径长期携带版本 |
| Header version | `API-Version: 2026-05-13` | 平台 API、需要细粒度版本 | 调试和缓存更复杂 |
| Media type version | `application/vnd.example.v1+json` | 强内容协商场景 | 客户端门槛较高 |
| GraphQL 字段演进 | 新字段替代旧字段 | GraphQL API | 依赖废弃标记和 schema 治理 |
| 事件 schema version | `schema_version` | 事件、Webhook、消息 | 消费者必须能多版本解析 |

同一个 API 域内不要混用多种策略，除非有清晰边界。

## 废弃生命周期

废弃不是删除前的一句通知，应有完整生命周期：

1. 标记废弃：文档、OpenAPI、schema 或 SDK 标记。
2. 公告替代方案：说明新接口、新字段或新流程。
3. 监控使用量：识别仍在调用旧契约的客户端。
4. 设置 sunset：给出最后支持日期。
5. 提供迁移指南：包含字段映射和调用示例。
6. 执行下线：返回明确错误或保持兼容层。
7. 清理 SSoT：同步长期文档和历史记录。

HTTP API 可使用 `Deprecation`、`Sunset`、`Link` 等响应头表达废弃和迁移信息。

## 破坏性变更要求

破坏性变更必须提供：

- 新版本或版本隔离方案。
- 调用方影响清单。
- 迁移指南和示例。
- 废弃公告和 sunset 时间。
- 灰度、监控和回滚计划。
- 是否需要兼容层。
- SSoT 更新计划。

## OpenAPI 和 SDK

版本变更必须同步：

- OpenAPI `info.version`。
- operation 的 `deprecated` 标记。
- schema 字段说明。
- SDK major / minor 版本。
- changelog。
- 契约测试。

不要只改服务端代码而不改契约文件。

## Review Checklist

- 是否判断了本次变更的兼容性。
- 是否有统一版本策略。
- 破坏性变更是否有迁移路径。
- 废弃是否有公告、替代方案和 sunset。
- OpenAPI / SDK / 文档 / 测试是否同步。
- 是否监控旧版本调用方。
