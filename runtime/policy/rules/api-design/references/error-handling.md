# API 错误处理

本参考用于设计统一、可处理、可排查且安全的错误响应。

## 标准错误形态

优先使用 RFC 7807 风格的 `application/problem+json`。如果项目已有统一错误包络，可以保留，但必须具备同等信息量。

推荐字段：

| 字段 | 说明 |
|---|---|
| `type` | 稳定的错误类型 URI，不要用临时字符串 |
| `title` | 简短、稳定、可展示的错误标题 |
| `status` | HTTP 状态码 |
| `detail` | 面向本次请求的可读说明 |
| `instance` | 本次错误实例或请求追踪路径 |
| `code` | 机器可读业务错误码 |
| `request_id` | 排查用请求 ID |
| `errors` | 字段级或多原因错误明细 |

字段级校验错误应包含字段路径、错误码、可读信息和约束信息。不要只返回“参数错误”。

## 错误分类

| 类型 | 状态码 | 设计要求 |
|---|---|---|
| 请求格式错误 | `400` | 说明哪个参数格式错误 |
| 认证失败 | `401` | 返回 `WWW-Authenticate` 或等价认证提示 |
| 授权失败 | `403` | 说明缺少权限类型，不泄露敏感资源 |
| 资源不存在 | `404` | 对不可见资源可同样返回 `404` |
| 状态冲突 | `409` | 说明冲突对象、当前状态和恢复方式 |
| 业务校验失败 | `422` | 返回字段级或规则级明细 |
| 限流 | `429` | 返回 `Retry-After` 和限流窗口信息 |
| 服务不可用 | `503` | 返回是否可重试和预计恢复信息 |

## 错误码目录

每个 API 域应维护错误码目录，至少包含：

- 错误码。
- 对应 HTTP 状态码。
- 触发条件。
- 调用方可采取的动作。
- 是否可重试。
- 是否应该展示给终端用户。
- 文档链接。

错误码必须稳定。文案可以优化，错误码不能随意改名。

## 请求追踪

所有错误响应都应能和日志关联：

- 响应头提供 `X-Request-ID` 或项目约定的 trace id。
- 响应体中可重复放置 `request_id`。
- 服务端日志必须记录同一个 id。
- 用户可见错误不要包含堆栈、SQL、内部路径、密钥、节点名和配置值。

## 重试语义

错误响应应帮助调用方判断是否重试。

通常可重试：

- `408`
- `429`，必须结合 `Retry-After`
- `500`，仅在项目明确允许时
- `502`
- `503`
- `504`

通常不可重试：

- `400`
- `401`
- `403`
- `404`
- `409`，除非先解决冲突
- `422`

## OpenAPI 要求

每个 operation 必须列出可能错误响应。至少不要只写一个泛化 `default`。

公共错误响应应抽到 `components.responses`，错误 schema 应抽到 `components.schemas`，示例应覆盖常见失败路径。

## Review Checklist

- 错误格式是否全 API 一致。
- 是否存在稳定错误码和文档链接。
- 字段级校验是否足够具体。
- 是否包含 request id。
- 认证、授权、资源不存在是否不会泄露敏感信息。
- 限流和服务不可用是否说明重试语义。
- OpenAPI 是否写出每个 operation 的错误响应。

## 反模式

- 所有失败都返回 `200`。
- 只返回 `error: true` 或 `message: failed`。
- 不同 endpoint 使用不同错误结构。
- 给客户端暴露堆栈、SQL、文件路径、内部服务名。
- 错误码和错误文案混在一起，导致客户端只能解析自然语言。
- 没有 request id，线上问题无法排查。
