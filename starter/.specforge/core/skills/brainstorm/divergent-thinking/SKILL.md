# 发散生成

本 skill 用于扩大方案空间。它不负责选择最终方案，也不替代事实查证；它负责让后续 `critic-review` 和 `decision-matrix` 有真正不同的候选可以比较。

## 前置输入

- `brainstorm.md#问题重构` 和 `#问题地图`。
- `research-source` 的事实证据；如果事实会影响可行性，先读证据再发散。
- 用户明确的非目标、固定约束和授权默认。

## 发散步骤

1. 写出核心目标：用一句话描述“真正要达成什么”。
2. 列出不可触碰约束：技术栈、成本、时间、合规、已有设计、用户习惯。
3. 从下面镜头生成方向，每个镜头至少产出 1 个候选。
4. 合并重复方向，但保留明显不同的策略。
5. 给每个方向标注类型、适用场景、主要代价、最大未知。
6. 至少保留一个“做少一点”的简化方向。
7. 至少保留一个挑战原始假设的反直觉方向。

## 发散镜头

| 镜头 | 提示 |
|---|---|
| 第一性原理 | 最小机制是什么？不依赖当前解法还能不能达到目标？ |
| 用户角色 | 普通用户、管理员、运营、开发、测试、安全分别最在乎什么？ |
| 时间尺度 | 1 天、1 个 sprint、1 个季度、长期演进分别怎么做？ |
| 成本反转 | 如果只有一天怎么做？如果维护成本最重要怎么做？如果预算充足怎么做？ |
| SCAMPER | 替换、组合、调整、放大、缩小、挪用、删除、重排。 |
| 反向失败 | 如果故意做差会怎么做？反过来能得到什么方向？ |
| 分层拆解 | 能力层、交互层、数据层、安全层、落地层、演进层分别有什么方案？ |

## 输出格式

```md
## 发散方向池

| 方向 | 类型 | 核心想法 | 适合场景 | 主要代价 | 最大未知 | 是否进入收敛 |
|---|---|---|---|---|---|---|
| 保守版 | low-cost | | | | | yes / no |
| 标准版 | balanced | | | | | yes / no |
| 激进版 | high-upside | | | | | yes / no |
| 实验版 | exploratory | | | | | yes / no |
| 反直觉版 | counterintuitive | | | | | yes / no |
```

## 数量要求

| Profile | 最小方向数 | 必须包含 |
|---|---:|---|
| `light` | 3 | 保守版、标准版、简化或反直觉方向 |
| `deep` | 5 | 保守版、标准版、激进版、实验版、反直觉版 |
| `research-heavy` | 2 | 至少一个低风险方向和一个依赖证据的方向 |

## 方向组合

发散后不要直接把所有方向丢给用户。先做一次轻量归并：

| 处理 | 使用条件 |
|---|---|
| 合并 | 两个方向目标相同，只是执行路径略有差异 |
| 拆分 | 一个方向同时包含产品、技术和验证三种决策 |
| 保留 | 方向机制不同，且会改变用户取舍 |
| 暂缓 | 方向有价值，但不属于当前 MVP 或证据不足 |
| 删除 | 方向只是在重复已有方案，或明显违反非目标 |

## 质量门槛

- 方案必须在机制上不同，不能只是措辞不同。
- 每个方向都要写代价和未知，不允许只写好处。
- 如果某方向依赖未查证事实，标记 `needs research`，不要把它写成可采纳。
- 不把发散结果写成用户已确认；只能写候选。
- 发散结束时必须标记哪些方向进入收敛，哪些方向暂缓或删除。

## 常见失败

| 失败 | 表现 | 修正 |
|---|---|---|
| 方案假多样 | A/B/C 都是同一方案换名字 | 回到发散镜头，要求机制不同 |
| 只给激进方案 | 好看但落不了地 | 补保守版和标准版 |
| 只给实现方案 | 忽略产品、体验、验证 | 按分层拆解补齐 |
| 不写代价 | 用户无法取舍 | 每项补成本、风险和未知 |

## 交接

- 把进入收敛的方向交给 `scenario-simulation` 和 `critic-review`。
- 如果方向依赖外部事实，交给 `research-source`。
- 如果方向太多，交给 `decision-matrix` 前先合并同类项。

## 自检清单

- 是否至少有一个低成本方向？
- 是否至少有一个挑战原假设的方向？
- 是否写了每个方向的代价和最大未知？
- 是否删除了只有措辞差异的重复项？
- 是否把证据依赖明确交给 `research-source`？
