# 分析深度规则

本规则把需求分析拆成可调深度的证据流程。它吸收“需求理解 → 代码探索 → 外部研究 → 澄清 → 深度分析 → 展示计划”的优点，但落到 SpecForge artifact 中，不另起一套并行状态机。

## 什么时候启用

- 新功能、复杂 bug、重构、API / 数据库设计、全栈应用、架构调整。
- 用户需求描述模糊，或存在多个合理方案。
- 涉及新框架、第三方库、部署、安全、权限、数据迁移或性能风险。

## 深度档位

| 档位 | 适用 | 必需动作 |
|---|---|---|
| `light` | 单文件、小修、低风险 | 需求理解、必要澄清、最小验证 |
| `standard` | 常规 feature / bugfix | 需求理解、代码库探索、澄清、分析综合、计划证据 |
| `deep` | 多模块、新技术栈、API / DB / 安全 / 部署 | standard 全部动作 + 外部官方资料研究 + 更严格 spec review |

## 证据包

`00-intake/brief.md` 必须记录：

- 需求理解：目标、角色、业务结果、关键实体。
- 代码库探索：相关模块、现有模式、约束和可复用部分；绿地项目写明“无既有实现”。
- 外部资源研究：触发原因、资料来源、关键结论；未触发时写明跳过原因。
- 澄清记录：问题、用户答案、确认的取舍和仍需防守的假设。
- 分析综合：从上述证据推导出的范围、风险、workflow 和下一步。

## 复杂需求澄清纪律

提问前先汇总：

- 已明确。
- 待确认。
- 可能遗漏。

问题应尽量给出 2-3 个互斥选项、影响说明和推荐选项。没有合适选项时再问开放问题。

## 外部研究纪律

满足以下任一条件时必须研究当前资料：

- 引入或升级框架、SDK、CLI、库、云服务或协议。
- 需要引用具体命令、参数、配置或版本。
- 安全、权限、部署、合规或生产风险。
- 仓库内示例不足以支撑方案。

优先官方文档、标准、项目 README / release notes。研究结论应进入 `brief.md` 或 `design.md`，不要大段复制资料。

## 计划确认

进入 implementation 前，非 `light` 变更的 `spec_review` evidence 必须能回答：

- 需求、设计和任务是否都可追溯到分析证据或用户确认。
- 用户是否已经确认 MVP / 关键取舍，或为何可以安全使用默认假设。
- 仍有哪些残余风险，implementation 如何防守。

## 并行探索和审查

复杂需求可以按架构层次或功能模块并行探索 / 审查，但只能在环境和用户允许时使用子代理。不能使用子代理时，用本地工具并行读取文件或由主流程完成探索。

## 停止条件

- 复杂需求没有分析深度档位。
- `standard` / `deep` 缺少代码库探索或明确跳过原因。
- `deep` 缺少外部研究或明确跳过原因。
- 关键澄清没有用户答案。
- spec review 不能把计划追溯到分析证据。
