# 边界审查和验证证据

本参考用于 code review、spec review 和 verification，确认边界不是“写过”，而是真的被执行了。

## 边界产物

| 产物 | 边界职责 |
|---|---|
| `brief.md` | 候选边界、owner 候选和 workflow 路由 |
| `requirements.md` | 范围、非目标、依赖、影响面、验收边界 |
| `design.md` | 边界承诺、写入范围、契约影响、回滚与验证边界 |
| `tasks.md` | 任务级 `_Boundary:_`、`_Depends:_`、`_Evidence:_` |
| `spec-review-v1.md` | 审查边界是否足以开始实现 |
| `code-review-v1.md` | 审查是否发生越界实现 |
| `verification/report.md` | 证明受影响边界已被验证 |
| `ssot-sync.md` | 长期契约和项目事实已回流 |

## 重点边界违规

审查时重点标记：

- 未更新规格就编辑批准范围外的文件。
- 给本变更增加属于其他 change 的责任。
- 把上游缺陷隐藏在下游补丁里。
- 创建没有明确 owner 的共享抽象。
- 契约变化后没有重新验证下游依赖。
- 为了通过测试而改变无关行为。
- 在没有迁移、兼容或回滚说明的情况下改变持久化数据结构。
- 在没有 SSoT sync 的情况下改变长期事实。
- 把“理解时读到的邻近代码”误当成“可以顺手修的范围”。

## 边界证据

每次 review 至少检查：

| 证据 | 必须确认 |
|---|---|
| `requirements.md` | 是否有范围、非目标、依赖、影响面 |
| `design.md` | 是否有写入范围、契约影响、回滚和验证边界 |
| `tasks.md` | 是否有任务依赖、任务边界和完成证据 |
| `changed-files.md` | 是否和批准的写入范围一致 |
| `verification/report.md` | 是否覆盖被影响的边界 |
| `ssot-sync.md` | 长期事实是否同步或明确无需同步 |

## spec review 关注点

- 范围是否单一而清楚。
- 非目标是否足以阻止 scope creep。
- owner 是否明确。
- 依赖和下游影响是否写清。
- 是否存在尚未承认的第二个 change。

## code review 关注点

- diff 是否和设计边界一致。
- 是否出现未声明行为。
- 是否出现未声明契约变化。
- 是否已经发生边界扩大却没更新 spec。
- 是否应该拆分后再 review。

## verification 关注点

- 测试是否覆盖所有受影响边界。
- 回归验证是否覆盖“必须保持不变”的行为。
- 公共契约变化是否验证了兼容性。
- 高风险路径是否有专门证据。

## 审查结论建议

如果边界不清，应阻断：

- `REQUEST_CHANGES`
- 原因写明是 scope、owner、写入范围还是验证边界不清。

不要用“建议后续补文档”掩盖当前边界已经失控的事实。
