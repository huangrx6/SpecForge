# 范围、Owner 和责任边界

本参考用于明确“这个 change 属于谁、负责什么、不负责什么、依赖谁、影响谁”。

## 必答问题

每个非 lite change 都应回答：

- 本次变更拥有什么责任？
- 本次变更明确不负责什么？
- 本次 change 的主要 owner 是谁？
- 依赖哪些上游契约？
- 会影响哪些下游系统、模块、用户路径或集成方？
- 如果契约变化，哪些区域必须重新验证？
- 是否涉及公共 API、数据库 schema、配置、权限、部署方式、数据迁移或长期文档？

## Owner 判断

| 类型 | owner 判断方式 |
|---|---|
| 功能 owner | 谁负责该能力的行为、验收和长期维护 |
| 数据 owner | 谁定义字段含义、生命周期、权限和迁移策略 |
| API owner | 谁定义入参、出参、错误码、兼容策略和文档 |
| UI owner | 谁负责交互、状态、空态、错误态和可访问性 |
| 运行 owner | 谁负责配置、部署、监控、告警和回滚 |

owner 不清楚时，不能靠猜继续推进。应记录：

```text
[NEEDS CLARIFICATION: owner]
```

## 范围与非目标

范围描述要尽量回答“本次 change 完成后，什么行为会变，什么行为不会变”。

推荐结构：

- In scope
- Out of scope
- Keep unchanged
- Dependencies
- Downstream impact

“不做什么”不是空话，它直接决定：

- tasks 不该出现什么。
- implementation 不该顺手动什么。
- review 应该拦住什么。

## 契约边界

需要显式列出的契约包括：

- API。
- 数据 schema。
- 事件 / Webhook。
- 权限。
- 配置。
- 部署约定。
- SSoT 文档。

契约变化必须说明：

- 是否兼容。
- 谁会受影响。
- 需要哪些验证。
- 是否需要迁移。
- 是否需要同步长期文档。

## 何时优先拆分

出现以下情况时，应优先拆 change：

- 同时改变多个 owner 的公共契约。
- 验收标准超过一个独立用户目标。
- 多个责任可以独立发布或回滚。
- 任何一个子任务失败都会让其他子任务难以审查。
- 代码审查必须频繁在“这个到底属不属于本 change”之间切换。

## Review Checklist

- 是否有单一主要 owner。
- 是否同时写清 in-scope 和 out-of-scope。
- 是否列出上下游契约。
- 是否明确哪些行为必须保持不变。
- 是否已经出现“其实是两个 change”的信号。
