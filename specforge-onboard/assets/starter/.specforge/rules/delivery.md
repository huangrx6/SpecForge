# 交付和运行规则

交付规则适用于配置、构建、发布、回滚、环境、日志、监控和上线准备。只要 change 影响运行时行为，就必须考虑本规则。

## 基本原则

- 构建、发布、运行应尽量分离。
- 环境差异通过配置表达，不通过改代码表达。
- 发布必须可重复，回滚必须可说明。
- 新能力上线后应能被观察、定位和关闭。
- 生产配置和密钥不进入仓库。

## 配置

- 配置项应有名称、含义、默认值、示例和生效范围。
- 配置校验失败应尽早失败，并给出可操作错误。
- 敏感配置通过环境变量、密钥系统或部署平台注入。
- 不把多个环境打包成一组巨大配置；配置项应尽量独立。
- Docker Compose、Kubernetes、CI/CD 中的环境变量变更必须写入 release 或 deployment 说明。

## 构建和发布

release 说明应包含：

- 发布内容。
- 构建版本、镜像、包或 commit。
- 目标环境。
- 配置变更。
- 数据迁移或兼容要求。
- 验证步骤。
- 回滚方式。

构建产物应可追溯到源码 commit。不要手工修改构建产物后发布。

## 回滚

回滚说明应写清：

- 回滚触发条件。
- 回滚命令或操作步骤。
- 是否需要回滚数据库、配置、缓存、消息或外部系统状态。
- 回滚后如何验证。
- 不可回滚项和补偿方案。

如果无法回滚，必须提供降级、开关、禁用入口或人工补偿方案。

## 日志和可观测性

- 日志应作为事件流输出，交由运行环境收集和路由。
- 关键链路应有 trace id、request id 或 correlation id。
- 新增后台任务、异步任务、同步链路、插件和网关能力，应能看到开始、成功、失败和耗时。
- 指标优先围绕用户可感知行为，例如可用性、延迟、错误率、吞吐和正确性。
- 告警应指向需要行动的问题，避免只因为日志出现就告警。

## 上线前检查

上线前至少确认：

- required gate 已批准。
- release 和 rollback 已写。
- 配置项、密钥和环境变量已准备。
- 迁移脚本或数据处理已验证。
- 监控、日志或手工观察方式已明确。
- 已知风险和验收缺口已记录。

## 生产问题处理

发现生产问题时：

- 先止血：回滚、降级、关闭开关或限制流量。
- 保留证据：日志、指标、版本、配置、时间线。
- 再定位根因，不在无证据情况下连续扩大修改。
- 修复后必须补充回归用例或运维检查项。
- 如果长期事实变化，更新 `.specforge/project/risks.md` 或 decisions。
