# 安全规则

安全规则适用于任何影响认证、授权、密钥、个人数据、生产配置、供应链、日志、外部集成或权限边界的变更。安全不是最后补一条测试，而是从 requirements、design、implementation、verification 到 closure 都必须留下证据。

## 基本原则

- 不提交密钥、token、私钥、明文密码或生产连接串。
- 身份认证、权限、token、个人数据、审计日志都按敏感内容处理。
- 默认最小权限、最小暴露、最小保留。
- 对安全有影响的长期决策必须记录到 `.specforge/project/decisions/`。
- 安全敏感 change 不允许跳过 code review 和 verification。

## 安全分类

只要命中任一项，就按安全敏感变更处理：

- 登录、单点登录、4A/IAM、OAuth、SAML、Session、JWT、API Key。
- 权限模型、角色、菜单、数据范围、租户隔离。
- 密码、密钥、证书、token、连接串、加密配置。
- 用户个人信息、组织数据、业务敏感数据、日志脱敏。
- 文件上传、解析、转换、导入导出。
- 外部回调、Webhook、消息队列、跨系统同步。
- Docker、Kubernetes、CI/CD、生产环境变量和发布脚本。
- 依赖升级、构建插件、代码生成器、第三方二进制。

## 密钥和配置

- 密钥不得硬编码在源码、模板、测试样例、日志或文档中。
- 生产密钥应通过环境变量、密钥管理系统或部署平台注入。
- 环境变量可以作为注入方式，但仍要避免在日志、错误提示、CI 输出中泄露。
- 配置文件中的密码必须加密、引用密钥管理系统，或使用部署时注入的占位符。
- 密钥应具备创建、轮换、吊销、过期和审计策略。
- 示例配置必须使用假值，例如 `example-password`，不得使用真实格式的生产 secret。
- 发现泄露时，不能只删除文件；必须轮换密钥，并评估 git 历史、日志和制品。

## 认证和授权

- 认证回答“你是谁”，授权回答“你能做什么”，设计中必须分开描述。
- 后端必须做权限校验，前端菜单或按钮隐藏不能作为唯一保护。
- 权限判断应基于服务端可信身份、角色、资源 owner 和数据范围。
- 默认拒绝，显式允许。
- 跨租户、跨组织、管理员角色和批量操作必须有额外验证。
- token 应有过期时间、撤销策略和作用域。

## 输入、输出和文件处理

- 所有外部输入都不可信，包括请求参数、消息、文件、环境变量、回调和数据库旧数据。
- 输入校验应靠 allowlist、结构化 schema 或类型系统，不靠字符串拼接判断。
- SQL、命令、模板、路径、HTML、JSON、XML 等上下文必须使用对应安全 API。
- 文件上传和转换必须限制类型、大小、路径、执行权限和解析器行为。
- 输出到页面、日志、错误响应或下游系统前，应按上下文编码或脱敏。

## 数据保护

- 收集数据前确认必要性。
- 存储敏感数据前确认加密、脱敏、访问控制和保留周期。
- 日志、监控、截图、测试数据和导出文件同样适用数据保护规则。
- 测试环境不得默认使用生产数据；必要时必须脱敏并限制访问。
- 删除或归档数据时要考虑审计和合规保留。

## 错误和日志

- 对外错误信息应稳定、简洁，不暴露堆栈、SQL、路径、版本、密钥或内部服务名。
- 安全事件必须记录足够审计信息，例如主体、资源、动作、结果、时间和 trace id。
- 日志不得记录明文 secret、完整 token、密码、私钥或敏感个人信息。
- 安全相关失败不能静默吞掉，至少要有可排查证据。

## 供应链和依赖

- 新增依赖前检查来源、维护状态、许可证和安装脚本风险。
- 构建脚本、GitHub Actions、Dockerfile、插件和代码生成器按可执行代码审查。
- 依赖升级应记录安全目的、兼容影响和验证结果。
- 不从不可信 URL 下载并执行脚本。

## 安全验证

安全敏感 change 至少需要：

- 权限正向和反向用例。
- 非法输入、越权、过期 token 或缺失凭据用例。
- 日志脱敏检查。
- 配置和密钥泄露检查。
- 回滚或禁用方案。
