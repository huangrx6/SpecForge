# 工程规则入口

本目录约束实现阶段的最低工程纪律。它不替代团队自己的语言规范、框架规范或安全规范，而是回答：

- 实现时怎样保持 change 小而可审查。
- 怎样避免“功能改动、重构、依赖升级、格式化”混成一团。
- 什么时候需要补配置、迁移、日志和可观测性。
- 完成实现后，应留下什么证据。

## 什么时候启用

遇到下面任一情况，必须读取本入口：

- 进入 design 或 implementation 阶段。
- 准备改业务代码、公共组件、配置、依赖或数据结构。
- 需要判断一个实现是否过度设计。
- 需要判断代码健康、迁移策略、观测能力或验证证据是否足够。

## 核心原则

- 改动必须限定在 active change 的范围内。
- 优先沿用当前项目已有模式、目录结构、命名、错误处理和测试方式。
- 不为了“看起来更优雅”引入新抽象。抽象必须服务当前重复、复杂度或边界问题。
- 行为变更、结构重构、依赖升级、格式化清理应尽量拆开。
- 如果代码变更影响长期项目知识，必须更新 `.specforge/knowledge/`。
- 给审查者留下足够证据，说明改了什么、为什么改、怎么验证。

Google Engineering Practices 强调小而自洽的 change、相关测试同 change、重构与行为变更尽量分离；这与 SpecForge 的实现纪律完全一致。

## 工程规则的职责边界

| 规则 | 主要负责 |
|---|---|
| `engineering/README.md` | 实现纪律入口 |
| `security/README.md` | 安全、密钥、权限、供应链风险 |
| `testing/README.md` | 验证深度、测试证据 |
| `delivery/README.md` | 构建、发布、部署、上线和回滚证据 |

如果一个问题同时属于多个领域，engineering 负责“实现阶段应想到它”，security / testing / delivery 负责“具体标准和证据要求”。

## 实现完成证据

implementation report 至少应说明：

- 改动摘要。
- 关键文件。
- 行为变化。
- 验证命令和结果。
- 未覆盖风险。
- 是否需要更新 SSoT。

## 反模式速记

- 还没读现有实现就开始重写。
- 为未来可能性引入抽象和依赖。
- 把大规模重构塞进一个功能 change。
- 新增外部服务但没有配置、超时、失败模式和回滚说明。
- 只在代码里加日志，却没有考虑 verification 和上线后观察。
